# ProtoLab — лаборатория протоколов

Локальный инструмент для исследования недокументированного бинарного обмена с устройством поверх TCP.
Инженер открывает записи трафика (PCAP/PCAPNG) и сопоставляет их с журналом действий в штатном клиенте.
Затем он формулирует интерпретацию, проверяет её на дополнительных записях и передаёт воспроизводимое
исследование другому инженеру.

ProtoLab — один исполняемый файл без зависимостей. При запуске в терминале открывается
терминальный интерфейс (TUI) с состоянием сервера. Клавиша `o` открывает подробный веб-интерфейс
в браузере. Веб-интерфейс встроен в бинарь и работает только на `127.0.0.1`, без интернета.

## Установка

Скачайте архив для своей системы со страницы [Releases](https://github.com/AVGsync/protolab/releases).
Каждое слияние в `main` публикует новую версию: тег `v<MAJOR.MINOR>.<N>` (например, `v0.1.7`), где
`MAJOR.MINOR` берётся из файла `VERSION`, а `N` — номер запуска workflow. Номера растут, но идут не
подряд: упавшие, отменённые и ручные запуски тоже занимают номер.

| Система | Архив |
|---|---|
| Linux x86-64 / ARM64 | `protolab_<версия>_linux_amd64.tar.gz` / `..._linux_arm64.tar.gz` |
| macOS Intel / Apple Silicon | `protolab_<версия>_darwin_amd64.tar.gz` / `..._darwin_arm64.tar.gz` |
| Windows x86-64 / ARM64 | `protolab_<версия>_windows_amd64.zip` / `..._windows_arm64.zip` |

`<версия>` — это тег без буквы `v`: релиз `v0.1.7` содержит `protolab_0.1.7_linux_amd64.tar.gz` и так далее.
В архиве один каталог `protolab_<версия>_<os>_<arch>/` с исполняемым файлом (`protolab`, на Windows
`protolab.exe`), этим `README.md` и `THIRD_PARTY_NOTICES.md` — лицензиями библиотек, вошедших в бинарь
(Go-модули, Go и пакеты веб-интерфейса, включая шрифты IBM Plex под SIL OFL). Рядом с архивами в релизе
лежит файл `SHA256SUMS`.

```bash
sha256sum -c SHA256SUMS --ignore-missing      # проверить загрузку (macOS: shasum -a 256 <архив>)
tar -xzf protolab_*_linux_amd64.tar.gz
./protolab_*_linux_amd64/protolab
```

Бинари не подписаны. На macOS снимите карантин: `xattr -d com.apple.quarantine protolab`.
На Windows SmartScreen может попросить подтверждения.

## Запуск

```bash
protolab                 # сервер + терминальный интерфейс
protolab --demo          # то же, и создать демо-проект ThermoLink TC-200, если проектов ещё нет
protolab --no-tui        # без TUI (сервисы, CI, Docker): журнал в stderr, Ctrl+C — выход
```

Терминальный интерфейс:

| Клавиша | Действие |
|---|---|
| `o` / `Enter` | открыть веб-интерфейс в браузере |
| `c` / `y` | скопировать адрес (OSC 52 — работает и по SSH) |
| `d` | создать демо-проект |
| `l` / `Tab` | журнал во весь экран (`↑↓`/`jk`, `PgUp`/`PgDn`, `g`/`G`, `Esc`) |
| `?` / `F1` | справка |
| `q` / `Ctrl+C` | остановить сервер и выйти; если идут фоновые задачи — после подтверждения (`y`, `Enter` или второй `Ctrl+C`) |

Если stdin или stdout не терминал (перенаправление в файл, systemd) или `TERM=dumb`, TUI не запускается: адрес
печатается в stderr, журнал идёт туда же, сервер работает до `SIGINT`/`SIGTERM`.

Флаги сервера:

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `--addr` | `127.0.0.1:7420` | адрес HTTP; если порт по умолчанию занят, берётся свободный |
| `--data` | см. ниже | каталог данных |
| `--open` | — | сразу открыть браузер |
| `--demo` | — | создать демо-проект, если проектов нет |
| `--no-tui` | — | без терминального интерфейса |
| `--max-capture-mb` | `512` | предел размера одной записи |
| `--debug` | — | подробный журнал |

Каталог данных: `$PROTOLAB_DATA`, иначе `~/.local/share/protolab` (Linux, учитывает `XDG_DATA_HOME`),
`~/Library/Application Support/ProtoLab` (macOS), `%LOCALAPPDATA%\ProtoLab` (Windows); если ничего из этого не
определено — `protolab-data` в текущем каталоге.
Каждый проект — папка `projects/<id>/` с `project.json`, исходными записями `captures/<sha256>.pcap` или `.pcapng` (расширение по формату записи)
и отчётами `reports/`.

## Командная строка без интерфейса

```bash
protolab demo [--data DIR]                     # создать демо-проект и выйти
protolab apply --spec interpretation.json --input capture.pcapng [--out results.json] [--port 5020] [--all] [--overlap first|last] [--strict]
protolab verify --examples examples.<имя>.v3.json [--spec F] [--base DIR]   # повторить проверку из отчёта
protolab version
```

`apply` разбирает запись по интерпретации тем же движком, что и веб-интерфейс, и пишет JSON с
сообщениями и сводкой (по умолчанию в stdout). Разбираются сессии порта устройства (`--port`, иначе
`transport.port` из интерпретации; `--all` — все сессии). С `--strict` код выхода `3`, если есть нарушения или
неполные сообщения.

`verify` берёт файл примеров из отчёта, находит исходные записи по их пути в проекте (`captures/<sha256>.pcap[ng]`
рядом с файлом примеров или до четырёх каталогов выше; `--base` задаёт корень явно), сверяет их SHA-256, заново
собирает потоки с настройками проверки, применяет интерпретацию и сравнивает сводку с сохранённой. При расхождении
код выхода `1`.

Передать исследование проще всего комплектом: на странице «Отчёты» кнопка «Комплект (.zip)»
(`GET /api/v1/reports/{id}/bundle`) скачивает архив с отчётом, интерпретацией, результатами, файлом примеров и
исходными записями. После распаковки проверка повторяется из этого каталога, путь можно указывать относительный:

```bash
unzip report.thermolink.v3.zip -d thermolink && cd thermolink
protolab verify --examples examples.thermolink.v3.json
```

Так же команда работает из папки отчёта внутри проекта (`projects/<id>/reports/<reportId>/`).

## Структура репозитория

```text
protolab/
├── cmd/protolab/        # main: TUI + сервер, команды demo/apply/verify
├── internal/
│   ├── pcap/            # чтение PCAP и PCAPNG (без libpcap и cgo)
│   ├── netpkt/          # разбор Ethernet/SLL/IPv4/TCP, контрольные суммы
│   ├── tcpflow/         # сборка TCP-сессий и направленных потоков по sequence numbers
│   ├── spec/            # формат интерпретации protolab/v1 и его проверка
│   ├── engine/          # кадрирование, разбор полей, проверка утверждений
│   ├── app/             # прикладной слой: проекты, анализ, проверки, отчёты
│   ├── store/           # хранение на диске, экспорт и импорт архивов
│   ├── jobs/            # фоновые задачи с прогрессом и отменой
│   ├── report/          # Markdown/JSON-отчёты
│   ├── server/          # HTTP API и раздача веб-интерфейса
│   ├── tui/             # терминальный интерфейс (Bubble Tea)
│   ├── demo/            # генератор демо-данных ThermoLink TC-200
│   └── webui/           # встраиваемая сборка фронтенда (go:embed)
├── frontend/            # React + TypeScript (Vite), Feature-Sliced Design
└── docs/
    ├── backend.md                # как устроен Go-код (подробно)
    ├── api.md                    # REST API frontend ↔ backend
    ├── design.md                 # визуальный язык веб-интерфейса
    ├── performance.md            # контрольная нагрузка, замеры и защитные пределы
    └── interpretation-format.md  # формат интерпретации protolab/v1
```

## Сборка из исходников

Нужны Go (версия в `go.mod`) и Node.js ≥ 20.19; для `make release-local` ещё `zip`, `unzip` и `curl`.

```bash
make build              # фронтенд + бинарь bin/protolab с встроенным интерфейсом
make run                # собрать и запустить
make test               # go test -race + vitest
make check              # gofmt, go vet, tsc, eslint и все тесты (основа проверок CI)
make release-local      # шесть платформ в dist/ вместе с THIRD_PARTY_NOTICES.md, как в релизе
make verify-dist        # проверить dist/ так же, как перед публикацией релиза
```

Разработка интерфейса: запустите `protolab --no-tui` и `make web-dev` — Vite на
`http://localhost:5173` проксирует `/api` на `127.0.0.1:7420`. Без бэкенда: `cd frontend && npm run dev:mock`
(эмулированное API на MSW).

## Релизы

`.github/workflows/release.yml` запускается на каждый push в `main` (то есть на каждое слияние) и
выполняет по порядку:

1. `verify` — те же проверки, что и для pull request (`ci.yml`: frontend, go, smoke-тест бинаря, сборка
   под все платформы). Если они не прошли, релиза нет.
2. `make web` — фронтенд собирается один раз и встраивается во все шесть бинарей.
3. `make release-local` — кросс-компиляция с `CGO_ENABLED=0` под linux, darwin и windows (amd64 и arm64),
   `scripts/notices.sh` собирает `THIRD_PARTY_NOTICES.md`, затем архивы и `SHA256SUMS` в `dist/`.
4. `make verify-dist` (`scripts/verify-dist.sh`) — шесть архивов, контрольные суммы, в каждом архиве бинарь,
   README и лицензии, у каждого бинаря собственные GOOS/GOARCH, лицензии покрывают все Go-модули из
   `go version -m` этого бинаря; бинарь linux/amd64 запускается, сообщает версию релиза и отдаёт веб-интерфейс.
5. `gh release create` — тег `v<VERSION>.<номер запуска>` на коммите слияния, GitHub Release с шестью
   архивами и `SHA256SUMS`; заметки генерирует GitHub (слитые PR с предыдущего релиза). У первого релиза
   предыдущего тега нет, и GitHub строит заметки без него.

Лицензии (`THIRD_PARTY_NOTICES.md`) создаются в шаге 3, а не хранятся в репозитории: список Go-модулей
берётся из `go list -deps` для каждой из шести платформ (он различается: например, `x/termios` не линкуется
в Windows-сборку) и объединяется; к нему добавляются Go и production-зависимости `frontend/`.

Повторный запуск того же прогона («Re-run jobs») не создаёт второй релиз: если тег уже указывает на тот же
коммит и релиз существует, публикация пропускается. Старый упавший запуск, перезапущенный после более
нового релиза, завершается ошибкой и ничего не публикует (иначе старая сборка стала бы «Latest»).

Ручной запуск (`workflow_dispatch`) выполняет шаги 1–4 на выбранной ветке, но ничего не публикует: архивы
можно скачать из вложений запуска (7 дней). Релизы выпускаются строго по одному; если за время одного запуска
в очередь встали два слияния, GitHub отменяет более раннее из ожидающих. Его изменения войдут в следующий
релиз вместе со своим PR в заметках.

Право `contents: write` (создать тег и релиз) запрашивает только задача публикации, остальным хватает
`contents: read`.

Локально то же самое: `make release-local VERSION=0.1.999 && make verify-dist VERSION=0.1.999`.

Подробное описание того, как работает Go-код, — в [docs/backend.md](docs/backend.md).
