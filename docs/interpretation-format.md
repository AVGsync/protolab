# Формат интерпретации `protolab/v1`

Интерпретация — это декларативное машиночитаемое описание протокола. Она хранится как JSON,
версионируется (каждое изменение даёт новую неизменяемую версию с SHA-256) и исполняется движком
backend. TypeScript-описание: `frontend/src/entities/interpretation/model/types.ts`. Эталонная
реализация движка для mock-режима: `frontend/src/mocks/engine/interpreter.ts`.

```jsonc
{
  "format": "protolab/v1",
  "protocol": "ThermoLink",
  "transport": { "port": 5020 },
  "framing": { ... },        // как выделять сообщения из потока
  "messages": [ ... ],       // типы сообщений и их поля
  "assertions": [ ... ]      // проверки по журналу действий
}
```

## Кадрирование (`framing`)

Граница TCP-сегмента не является границей сообщения. Поддерживаются три способа:

| `kind` | Поля | Семантика |
|---|---|---|
| `length_prefixed` | `lengthField {offset, size: 1\|2\|4, endian: le\|be}`, `lengthAdjust`, `minLength?`, `maxLength?`, `sync?` | полная длина = значение поля длины + `lengthAdjust` |
| `delimiter` | `delimiter` (hex), `sync?` | сообщение заканчивается разделителем |
| `fixed` | `size` | все сообщения одного размера |

`sync` — hex-шаблон для ресинхронизации. Он нужен, если неизвестен заголовок (пропуск в записи,
начало соединения не захвачено) или длина вне `[minLength, maxLength]`. Байты, пропущенные
при поиске синхронизации, попадают в находки проверки как «байты вне сообщений».
Если пропуск задел только тело сообщения, кадрирование остаётся выровненным: длина известна из
заголовка, а seq-номера TCP дают точный размер пропуска. Сообщение получает статус `partial`.

## Сообщения (`messages[]`)

```jsonc
{
  "id": "set_param_req",                 // уникальный id правила
  "title": "Изменение настройки — запрос",
  "direction": "c2s",                    // c2s | s2c | any
  "match": [{ "offset": 0, "hex": "A5" }, { "offset": 1, "hex": "02" }],  // все условия должны выполниться
  "hypothesis": "h-04",
  "fields": [ ... ]
}
```

Статус сообщения: `ok`; `violation` — поле нарушает ожидание, контрольную сумму или проверку по журналу;
`partial` — содержит неизвестные байты или обрезано; `ambiguous` — подходят несколько правил, разбор
идёт по первому; `unknown_type` — ни одно правило не подошло.

## Поля (`fields[]`)

| Ключ | Описание |
|---|---|
| `name` | имя поля (уникально в пределах уровня) |
| `offset` | смещение в сообщении; **отрицательное — от конца** (`-1` — последний байт) |
| `type` | `u8 i8 u16 i16 u32 i32 bytes ascii array` |
| `endian` | `le` (по умолчанию) или `be` |
| `length` | для `bytes`/`ascii`: число или имя ранее разобранного поля |
| `count`, `itemSize`, `items` | для `array`: имя поля-счётчика, размер элемента, поля элемента (смещения относительно начала элемента) |
| `scale`, `unit` | отображаемое значение = raw × scale |
| `enum` | `{"1": "уставка", ...}` — значение вне перечисления является нарушением |
| `expect` | `{equals?, min?, max?, oneOf?}` — проверяется по raw-значению |
| `checksum` | `sum8` или `xor8` по байтам сообщения `[0, offset)` |
| `meaning` | предполагаемое назначение (текст) |
| `status` | основание смысла: `structural` (структура подтверждается правилами, смысл не утверждается), `hypothesis`, `confirmed` |
| `hypothesis` | id гипотезы, на которой основан смысл |

Байты сообщения, не покрытые ни одним полем, возвращаются в `Message.unknown`. В сводке
проверки они учитываются как неописанные. Частичная интерпретация допустима: границы
известного видны всегда.

## Проверки по журналу действий (`assertions[]`)

Связывают поле с условиями эксперимента: «после действия "задать 21" поле `value` равно 21».

```jsonc
{
  "id": "a-set-value",
  "rule": "set_param_req",
  "actionKind": "set_param",
  "checks": [
    { "field": "param_id", "equals": "params.paramId" },
    { "field": "value",    "equals": "params.value" }
  ],
  "hypothesis": "h-04"
}
```

Проверка применяется к сообщениям правила `rule` в сессиях, связанных с действием вида
`actionKind`. Значение поля берётся с учётом `scale` и сравнивается с `params.<имя>` или
`observed.<имя>` действия. Несовпадение — нарушение поля с указанием действия. В отчёте оно
становится контрпримером к гипотезе.

## Повторное применение

Сохранённая версия применяется к новым данным без UI. Так выглядят команды CLI, которые печатает
отчёт:

```bash
protolab apply  --spec interpretation.thermolink.v3.json --input new.pcapng --out results.json
protolab verify --spec interpretation.thermolink.v3.json --examples examples.thermolink.v3.json
```

`examples.*.json` — входные сессии (запись + sha256 + номер tcp.stream) и ожидаемые сводки.
`verify` сравнивает результат применения с ожидаемым и возвращает ненулевой код при расхождении.
