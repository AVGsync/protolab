# Формат интерпретации `protolab/v1`

Интерпретация — это декларативное машиночитаемое описание протокола. Она хранится как JSON,
версионируется (каждое изменение даёт новую неизменяемую версию с SHA-256) и исполняется движком
`internal/engine`; проверку формата выполняет `internal/spec`. Описания типов: `internal/spec/spec.go`
и `frontend/src/entities/interpretation/model/types.ts`. Движок mock-режима
(`frontend/src/mocks/engine`) повторяет поведение Go-движка для разработки интерфейса без сервера;
отличия перечислены в разделе «Точная семантика».

```jsonc
{
  "format": "protolab/v1",
  "protocol": "ThermoLink",
  "transport": { "port": 5020 },
  "framing": { ... },        // как выделять сообщения из потока
  "messages": [ ... ],       // типы сообщений и их поля
  "assertions": [ ... ]      // проверки по журналу действий
}
```

## Кадрирование (`framing`)

Граница TCP-сегмента не является границей сообщения. Поддерживаются три способа:

| `kind` | Поля | Семантика |
|---|---|---|
| `length_prefixed` | `lengthField {offset, size: 1\|2\|4, endian: le\|be}`, `lengthAdjust`, `minLength?`, `maxLength?`, `sync?` | полная длина = значение поля длины + `lengthAdjust` |
| `delimiter` | `delimiter` (hex), `sync?` | сообщение заканчивается разделителем |
| `fixed` | `size` | все сообщения одного размера |

`sync` — hex-шаблон для ресинхронизации. Он нужен, если неизвестен заголовок (пропуск в записи,
начало соединения не захвачено) или длина вне `[minLength, maxLength]`. Байты, пропущенные
при поиске синхронизации, попадают в находки проверки как «байты вне сообщений».
Если пропуск задел только тело сообщения, кадрирование остаётся выровненным: длина известна из
заголовка, а seq-номера TCP дают точный размер пропуска. Сообщение получает статус `partial`.

## Сообщения (`messages[]`)

```jsonc
{
  "id": "set_param_req",                 // уникальный id правила
  "title": "Изменение настройки — запрос",
  "direction": "c2s",                    // c2s | s2c | any
  "match": [{ "offset": 0, "hex": "A5" }, { "offset": 1, "hex": "02" }],  // все условия должны выполниться
  "hypothesis": "h-04",
  "fields": [ ... ]
}
```

Статус сообщения: `ok`; `violation` — поле нарушает ожидание, контрольную сумму или проверку по журналу;
`partial` — содержит неизвестные байты или обрезано; `ambiguous` — подходят несколько правил, разбор
идёт по первому; `unknown_type` — ни одно правило не подошло.

## Поля (`fields[]`)

| Ключ | Описание |
|---|---|
| `name` | имя поля (уникально в пределах уровня) |
| `offset` | смещение в сообщении; **отрицательное — от конца** (`-1` — последний байт) |
| `type` | `u8 i8 u16 i16 u32 i32 bytes ascii array` |
| `endian` | `le` (по умолчанию) или `be` |
| `length` | для `bytes`/`ascii`: число или имя ранее разобранного поля |
| `count`, `itemSize`, `items` | для `array`: имя поля-счётчика, размер элемента, поля элемента (смещения относительно начала элемента) |
| `scale`, `unit` | отображаемое значение = raw × scale |
| `enum` | `{"1": "уставка", ...}` — значение вне перечисления является нарушением |
| `expect` | `{equals?, min?, max?, oneOf?}` — проверяется по raw-значению |
| `checksum` | `sum8` или `xor8` по байтам сообщения `[0, offset)` |
| `meaning` | предполагаемое назначение (текст) |
| `status` | основание смысла: `structural` (структура подтверждается правилами, смысл не утверждается), `hypothesis`, `confirmed` |
| `hypothesis` | id гипотезы, на которой основан смысл |

Байты сообщения, не покрытые ни одним полем, возвращаются в `Message.unknown`. В сводке
проверки они учитываются как неописанные. Частичная интерпретация допустима: границы
известного видны всегда.

## Проверки по журналу действий (`assertions[]`)

Связывают поле с условиями эксперимента: «после действия "задать 21" поле `value` равно 21».

```jsonc
{
  "id": "a-set-value",
  "rule": "set_param_req",
  "actionKind": "set_param",
  "checks": [
    { "field": "param_id", "equals": "params.paramId" },
    { "field": "value",    "equals": "params.value" }
  ],
  "hypothesis": "h-04"
}
```

Проверка применяется к сообщениям правила `rule` в сессиях, связанных с действием вида
`actionKind`. Значение поля берётся с учётом `scale` и сравнивается с `params.<имя>` или
`observed.<имя>` действия. Несовпадение — нарушение поля с указанием действия. В отчёте оно
становится контрпримером к гипотезе.

## Проверка спецификации

Спецификация разбирается строго: неизвестный ключ, лишние данные после JSON и неверный тип значения —
ошибки с путём вида `$.messages[0].fields[1].scale`. Кроме структуры проверяется:

- `framing.kind` — `length_prefixed`, `delimiter` или `fixed`; для `fixed` — `size > 0`; для
  `length_prefixed` — `lengthField.size` ∈ {1, 2, 4} и `lengthField.offset ≥ 0`; `endian` — `le` или `be`;
- `direction` — `c2s`, `s2c` или `any`; `match[].offset ≥ 0`; hex-строки корректны;
- `count` и `length`-ссылка указывают на **предыдущее целочисленное** поле того же уровня;
  `itemSize` и числовой `length` неотрицательны;
- `checksum` — `sum8` или `xor8`; `status` — `structural`, `hypothesis` или `confirmed`;
- `format` — ровно `protolab/v1`; `id` правил и имена полей одного уровня уникальны;
- `assertions[].rule` ссылается на существующее правило, `checks[].equals` имеет вид `params.<имя>` или `observed.<имя>`.

Предупреждения (не мешают сохранению): нет имени протокола, нет ни одного правила, правило без `match`
(совпадёт с любым сообщением), `length_prefixed` без `sync` (после пропуска разбор не восстановится).

Невалидную спецификацию нельзя сохранить как версию и нельзя запустить в проверке.

## Точная семантика

| Ситуация | Поведение |
|---|---|
| `minLength` не задан | минимальная длина = `lengthField.offset + lengthField.size`, но не меньше 1 (сообщение нулевой длины не продвигает разбор) |
| `maxLength` не задан | 65 600 байт (64 КиБ + 64) |
| длина вне `[minLength, maxLength]` или отрицательная | при заданном `sync` — поиск следующего шаблона, иначе байт становится неразобранным и разбор продолжается со следующего |
| поле длины попало в пропуск записи | граница сообщения неизвестна: разбор переходит за пропуск и ищет `sync` |
| пропуск внутри тела | сообщение `partial`, поля на неизвестных байтах — статус `unknown`, значение не вычисляется из заполнителя |
| `match` и разделитель | никогда не совпадают на неизвестных байтах; поиск разделителя не перекрывается (`00 00` в `00 00 00` — одно совпадение) |
| кадр только из неизвестных байтов | не создаётся; диапазон описан как дефект записи |
| `checksum` при неизвестных байтах в `[0, offset)` | не проверяется: несовпадение было бы ошибкой записи, а не протокола |
| отрицательный `scale` | число знаков после запятой берётся по `|scale|` |
| значение в `checks` | число JSON или числовая строка (`"21"`, `" -5.5 "`, `"0x15"`); пустая строка, `null` и логические значения числами не считаются, такая проверка не применяется |
| несколько действий одного вида в сессии | значения берутся из первого связанного действия этого вида |

## Повторное применение

Сохранённая версия применяется к новым данным без UI. Так выглядят команды CLI, которые печатает
отчёт:

```bash
protolab apply  --spec interpretation.thermolink.v3.json --input new.pcapng --out results.json
protolab verify --examples examples.thermolink.v3.json
```

`examples.*.json` (`protolab-examples/v1`) — имя файла спецификации и её хеш, версия движка, настройки
восстановления потоков и корпуса: каждая сессия задана записью (путь в проекте и SHA-256), номером
`tcp.stream` и конечными точками, рядом лежит ожидаемая сводка проверки. `verify` находит записи
(`--base` или вверх от файла примеров), сверяет их SHA-256, заново собирает потоки, применяет
интерпретацию (или другую через `--spec`) и сравнивает сводки. При расхождении код выхода `1`.
`apply --strict` возвращает `3`, если есть нарушения или неполные сообщения.
