# Бэкенд ProtoLab: как устроен Go-код

Документ объясняет, **что именно делает Go-часть ProtoLab и как это сделано**: от запуска процесса и разбора байтов
PCAP до проверки интерпретации на корпусе и переноса проекта. Он написан так, чтобы по нему можно было
пересказать и защитить бэкенд перед специалистами по протоколам, сетям и Go.

Соглашения:

- Ссылки на код даны как `путь/к/файлу.go` и имя функции или типа (`пакет`: `Тип.метод`). Номера строк не указаны
  намеренно: они уходят при каждой правке. Любое утверждение ниже можно проверить поиском по этому имени.
- Все пути `internal/...` относятся к корню репозитория.
- «Поток» — это направленный поток байтов TCP (клиент→сервер `c2s` или сервер→клиент `s2c`), восстановленный по
  номерам последовательности. «Сессия» — один экземпляр TCP-соединения.
- Где поведение — не требование ТЗ, а осознанное решение или эвристика, это сказано прямо. Список того, чего код
  не умеет, собран в разделе 17.

Содержание: 1. Коротко · 2. Процесс и жизненный цикл · 3. Карта пакетов · 4. Импорт записи · 5. Движок интерпретаций ·

## 1. Коротко

1. ProtoLab — **один статически собранный бинарь** (`cmd/protolab`, Go 1.25, `CGO_ENABLED=0`, шесть платформ):
   без libpcap, без внешних сервисов, без сети.
2. Внутри процесса живут три «лица» одного ядра: **HTTP-сервер** на `127.0.0.1` с встроенным React-интерфейсом
   (`//go:embed all:dist`), **терминальный интерфейс** (Bubble Tea) с горячей клавишей `o` «открыть в браузере» и
   **CLI-подкоманды** `demo`, `apply`, `verify`, `version`.
3. Ядро — слой `internal/app`: он хранит проекты, запускает фоновые задачи и превращает записи трафика в сессии,
   потоки, сообщения и результаты проверок. HTTP и TUI — тонкие адаптеры над ним.
4. **Конвейер данных:** файл PCAP/PCAPNG → `pcap` (кадры) → `netpkt` (Ethernet/IPv4/TCP) → `tcpflow` (сессии и
   потоки по sequence numbers, с пропусками, конфликтами, происхождением каждого байта) → `engine` (кадрирование,
   правила, поля, утверждения по журналу действий) → проверка на корпусе → отчёт.
5. **Исходные записи неизменяемы:** файл кладётся под именем своего SHA-256 и больше не открывается на запись;
   всё остальное (сессии, потоки, сообщения) детерминированно восстанавливается из него и не хранится.
6. **Неизвестное остаётся неизвестным:** пропуск в записи — это диапазон `Gap`, а не нули. Движок не читает такие
   байты как данные, не сопоставляет по ним правила и разделители, не проверяет по ним контрольные суммы.
7. **Интерпретация** — декларативный JSON `protolab/v1`; каждая версия неизменяема и имеет SHA-256 канонического
   JSON. Результат проверки привязан к версии, корпусу и настройкам и помечается `stale`, а не удаляется.
8. **Происхождение:** любой вывод (находка, наблюдение, контрпример) ссылается на точные байты:
   `SourceRef` = запись (+SHA-256) + сессия + направление + смещение/длина + номера пакетов.
9. **Воспроизводимость:** `protolab apply` и `protolab verify` вызывают те же функции, что и интерфейс; вывод
   побайтно детерминирован (проверено: два запуска `apply` дают одинаковый SHA-256 результата).
10. **Устойчивость:** повреждённая запись, оборванный файл, одна сломанная сессия или одна паника не останавливают
    остальное; превышение пределов всегда даёт явную ошибку или диагностику, а не молчаливое усечение.

## 2. Процесс и жизненный цикл

### 2.1. `main`: выбор режима

`cmd/protolab/main.go` (`main`) смотрит на первый аргумент:

| Аргумент | Что происходит |
|---|---|
| `version`, `--version`, `-v` | печатает `protolab <версия> (commit …, built …, os/arch)` и выходит |
| `help`, `-h`, `--help` | справка (`usage`), в ней подставляется каталог данных по умолчанию |
| `demo` | `runDemo` → создаёт демо-проект и выходит |
| `apply` | `runApply` → применяет интерпретацию к записи без интерфейса |
| `verify` | `runVerify` → повторяет проверку из отчёта |
| что угодно другое (включая пустой список и флаги) | `runServe(args)` — сервер и интерфейс; лишнее слово вместо подкоманды даёт ошибку «неизвестная команда» |

Переменные `version`, `commit`, `date` задаются линкером: `-ldflags "-X main.version=… -X main.commit=… -X main.date=…"`
(`Makefile`, переменная `LDFLAGS`); без них — `dev` / `none` / `unknown`. Код возврата процесса — это значение,
которое вернула `run*` (`os.Exit`).

Каталог данных (`defaultDataDir`): `$PROTOLAB_DATA`; иначе Windows — `%LOCALAPPDATA%\ProtoLab`, macOS —
`~/Library/Application Support/ProtoLab`, остальные — `$XDG_DATA_HOME/protolab` или `~/.local/share/protolab`;
если ничего не определено — `./protolab-data`.

### 2.2. Флаги сервера

`parseServeFlags` (`cmd/protolab/serve.go`) использует стандартный `flag` с `ContinueOnError` и выводом в `io.Discard`
(ошибки печатает `fail`, не `flag`):

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--addr` | `127.0.0.1:7420` | адрес HTTP |
| `--data` | `defaultDataDir()` | каталог данных |
| `--no-tui` | выкл. | не запускать терминальный интерфейс |
| `--open` | выкл. | открыть браузер сразу после старта |
| `--demo` | выкл. | создать демо-проект, если проектов ещё нет |
| `--max-capture-mb` | `512` | предел размера одной записи, МиБ (должен быть > 0) |
| `--debug` | выкл. | уровень журнала `Debug` вместо `Info` |

Лишний позиционный аргумент — ошибка («неизвестная команда …»). Признак «адрес задан явно» (`addrGiven`) вычисляется
через `fs.Visit` — он нужен для запасного порта (ниже).

### 2.3. `runServe`: последовательность запуска

```text
parseServeFlags
   │
   ├─ interactive = !--no-tui && stdout — терминал && stdin — терминал && TERM != "dumb"
   ├─ журнал: logx.NewRing(500) + logx.NewHandler(ring, level, mirror)   mirror = stderr, если не interactive
   │          slog.SetDefault(logger)  — туда же уходит и стандартный пакет log
   ├─ limits = app.DefaultLimits(); limits.MaxCaptureBytes = --max-capture-mb << 20
   ├─ app.New(...)  ── store.Open → создаёт <data>/projects; RemoveStaleTemp(1 ч); jobs.NewManager(ctx);
   │                    store.List() → newProject + register + failInterrupted + resumeIndexing для каждого проекта
   ├─ listen(f)     ── net.Listen(--addr); если порт по умолчанию занят и --addr не задан → 127.0.0.1:0
   ├─ http.Server{Handler: server.New(...), ReadHeaderTimeout 10 с, IdleTimeout 2 мин, ErrorLog → slog}
   ├─ go srv.Serve(ln)
   ├─ signal.NotifyContext(Background, SIGINT, SIGTERM)  → ctx
   ├─ a.Preload()               — в фоне анализирует все записи всех проектов
   ├─ --demo  → safeGo: CreateDemoProject(ctx), если проектов нет
   ├─ --open  → safeGo: browser.Open(url)
   ├─ interactive → tui.Run(ctx, …)      иначе → печать адреса в stderr и ожидание ctx.Done()/ошибки сервера
   └─ srv.Shutdown(5 с) → (defer) a.Close(): отмена задач и ожидание их завершения
```

Подробности и причины:

- **`app.New`** (`internal/app/app.go`): открывает хранилище, удаляет временные файлы старше часа, оставленные убитым
  процессом (`Store.RemoveStaleTemp`, 8.1), создаёт корневой контекст приложения `a.ctx`
  (отменяется в `Close`), менеджер задач `jobs.Manager` с этим контекстом, затем `store.List()` загружает каждую папку
  `projects/<id>/` с `project.json`. Проект, который не удалось прочитать (битый JSON, схема новее поддерживаемой),
  попадает в журнал как `project skipped` — **остальные проекты загружаются**. Для каждого загруженного проекта
  вызываются `failInterrupted` и `resumeIndexing`. Первая помечает проверки в статусе `running`/`queued` и отчёты
  `pending`, оставшиеся от процесса, убитого посреди работы, как `failed` (у проверки — `error` «Прервано: сервер был
  остановлен во время выполнения»): задачи, которая их завершила бы, больше нет (раздел 10). Вторая заново индексирует
  новой задачей записи со статусом `indexing` (процесс остановился посреди импорта) — файл уже лежит на диске (раздел 4.1).
- **Выбор адреса** (`listen`): `net.Listen("tcp", f.addr)`. Если порт по умолчанию `7420` занят **и** `--addr` не
  указывали, берётся свободный порт на `127.0.0.1:0`. Если `--addr` указан явно и занят — это ошибка, код выхода `1`.
  Реальный адрес берётся из `ln.Addr()` (`serverURL`): в URL стоит тот IP, к которому привязан сервер (`[::1]`,
  `127.0.0.2` — по `127.0.0.1` они недоступны), и `127.0.0.1` только при прослушивании всех интерфейсов (`0.0.0.0`),
  поэтому печатаемый и открываемый URL верен (`TestServerURL`).
- **Не-loopback адрес.** Если пользователь явно привязал сервер к не-loopback адресу (`--addr 0.0.0.0:7420`),
  `server.Options.AllowAnyHost` включается (проверки `Host`/`Origin` отключаются) и в журнал пишется предупреждение
  «сервер доступен из сети» (раздел 11.5).
- **`http.Server`:** заданы `ReadHeaderTimeout` (защита от медленных заголовков) и `IdleTimeout`; `ReadTimeout` и
  `WriteTimeout` **не заданы** намеренно — загрузка записи до 512 МиБ и выгрузка архива проекта идут потоком.
  `ErrorLog` перенаправлен в `slog`: иначе `net/http` писал бы в stderr поверх TUI.
- **`Preload`** (`app.go`): по горутине на проект; каждая последовательно вызывает `p.analysis(captureID)` для всех
  записей. Результат кэшируется в «слоте» анализа (раздел 13.2), поэтому первое открытие страницы быстрое, а SHA-256
  каждой записи заново проверяется при старте (раздел 7.3).

### 2.4. TUI или `--no-tui`

| Условие | Поведение |
|---|---|
| `--no-tui`, либо stdout/stdin не терминал (файл, pipe, systemd), либо `TERM=dumb` | TUI **не запускается**; журнал дублируется в stderr (`mirror`), печатается строка `ProtoLab <версия> — откройте <URL> (Ctrl+C — выход)`; процесс ждёт `ctx.Done()` или ошибку `srv.Serve` |
| терминал | `tui.Run(ctx, …)` занимает экран; журнал не пишется в stderr (его показывает панель журнала TUI) |
| `tui.Run` вернул `ErrNotTerminal` (проверка внутри `Run` не прошла) | журнал снова зеркалится в stderr, выполняется ветка «без терминала» |
| `tui.Run` вернул другую ошибку | запись в журнал, ветка «без терминала»: **сервер продолжает работать** до Ctrl+C |
| TUI завершился штатно (`q` или сигнал) | `printExitSummary` печатает в stderr последние ≤10 предупреждений/ошибок из кольца журнала и строку «ProtoLab остановлен.» |

Подробнее о самом TUI — раздел 12.

### 2.5. Сигналы и остановка

`signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)` даёт единый контекст `ctx`. Он передаётся
в `tui.Run` (`tea.WithContext`), а собственный обработчик сигналов Bubble Tea отключён (`tea.WithoutSignalHandler`) —
сигналами владеет `main`. В режиме TUI терминал в «сыром» режиме, поэтому `Ctrl+C` приходит как нажатие клавиши и обрабатывается привязкой «выход» (с подтверждением, если идут задачи); внешний `SIGTERM`/`SIGINT` отменяет `ctx`, и `tui.Run`
возвращает `nil` (`ErrInterrupted` / `ErrProgramKilled` при отменённом контексте считаются штатным выходом).

Порядок остановки (`runServe`, конец функции):

1. `srv.Shutdown` с таймаутом 5 с: новые соединения не принимаются, текущие запросы дорабатывают. Если за 5 с не
   успели, ошибка игнорируется и процесс завершается.
2. Отложенный `a.Close()` (`defer`, поэтому выполняется после `return`): `a.stop()` отменяет корневой контекст
   приложения → отменяются контексты всех задач; затем `a.jobs.Wait()` ждёт возврата каждого тела задачи.
3. Что происходит с задачами при остановке (`internal/app/captures.go`, `indexCapture`):
   импорт записи, прерванный остановкой программы (`a.ctx.Err() != nil`), **оставляет файл и запись `indexing`** —
   при следующем запуске `resumeIndexing` продолжит; отмена пользователем, наоборот, удаляет файл и запись
   (запись можно импортировать снова). Проверка (`executeRun`) при отмене сохраняет статус `cancelled`, отчёт —
   `failed`. После жёсткого завершения (`kill -9`, потеря питания) проверка остаётся `running`, а отчёт `pending` в
   `project.json`; их переводит в `failed` `failInterrupted` при следующем запуске (2.3).

### 2.6. Горутины и контексты

| Горутина | Кто создаёт | Чем останавливается |
|---|---|---|
| цикл `srv.Serve` + по горутине на соединение | `net/http` | `srv.Shutdown` |
| тело каждой фоновой задачи (`import_capture`, `import_project`, `verification`, `report`) | `jobs.Manager.Start` | контекст задачи ← `a.ctx` ← `Close()`; или `Cancel` |
| `Preload`: по горутине на проект | `App.Preload` | проверка `a.ctx.Err()` между записями; сам анализ получает `a.ctx` |
| повторный анализ после смены настроек проекта | `App.UpdateProject` | то же: анализ идёт с `a.ctx` |
| `--demo` и `--open` | `safeGo` (перехват паники в журнал) | сами завершаются |
| цикл Bubble Tea, команды `tea.Tick`/`tea.Cmd` | `internal/tui` | `tea.Quit` или отмена `ctx` |
| ожидание дочернего процесса браузера (`cmd.Wait`) | `browser.Open` | процесс всегда дожидается (нет зомби) |
| горутина `signal.NotifyContext` | стандартная библиотека | `stop()` в `defer` |

Важное следствие: лениво запрошенный анализ записи (первое обращение из HTTP-запроса) выполняется под контекстом
**приложения**, а не запроса (`project.analysis` → `analyzeFile(p.app.ctx, …)`). Закрытие вкладки браузера не отменяет
расчёт, который ждут другие вызывающие; отменяет его только остановка программы.

### 2.7. Подкоманды без интерфейса

`demo`, `apply`, `verify` не поднимают HTTP и TUI. `demo` создаёт `app.App` с журналом уровня `Warn` в stderr и вызывает
`CreateDemoProject` (отмена по `Ctrl+C`). `apply` и `verify` вообще не создают `App`: они вызывают `app.AnalyzeFile` и
`engine.*` напрямую (раздел 9).

## 3. Карта пакетов

### 3.1. Зависимости

Диаграмма и таблица составлены по `go list -f '{{.Imports}}'` (только внутренние пакеты). Циклов нет; нижние пакеты не
знают о верхних.

```text
 вход       cmd/protolab
              │  импортирует адаптеры, app и engine/report/spec/model для CLI
 адаптеры   server · tui · browser · logx · webui
              │  server → app;  tui → model (данные получает через интерфейс Source)
 сервис     app
              │  импортирует весь домен и основу
 домен      engine · tcpflow · report · store · jobs · demo
              │
 основа     netpkt ──► pcap          spec          model ──► spec
```


| Пакет | Импортирует (внутренние) |
|---|---|
| `pcap`, `spec`, `browser`, `logx`, `webui` | — |
| `netpkt` | `pcap` |
| `model` | `spec` |
| `tcpflow` | `model`, `netpkt` |
| `engine` | `model`, `spec` |
| `store`, `jobs`, `tui` | `model` |
| `report` | `model`, `spec` |
| `demo` | `model`, `netpkt`, `pcap`, `spec` |
| `app` | `demo`, `engine`, `jobs`, `model`, `netpkt`, `pcap`, `report`, `spec`, `store`, `tcpflow` |
| `server` | `app`, `jobs`, `model` |
| `cmd/protolab` | `app`, `browser`, `engine`, `logx`, `model`, `report`, `server`, `spec`, `tui`, `webui` |

Правило, которое достаточно помнить: **`pcap`, `spec`, `browser`, `logx` ни от чего своего не зависят; `netpkt` зависит
только от `pcap`; `tcpflow` — от `netpkt` и `model`; `engine` — от `model` и `spec`; `app` склеивает всё; `server` и
`tui` — тонкие адаптеры.** `tui` даже не импортирует `app`: интерфейс получает данные через `tui.Source`.

### 3.2. Пакеты: ответственность, ключевые типы, чего они сознательно не делают

## 4. Импорт записи: от байтов файла до сессий

Общая схема (все стрелки — вызовы внутри одного процесса):

```text
 браузер                server               app                          jobs / фон
 ───────                ──────               ───                          ──────────
 multipart ──► uploadCapture ──► ImportCapture ──► storeUpload:
                MaxBytesReader        │            tmp ◄─ io.Copy ─ body ─┬─► sha256
                                      │                                   └─► первые 4 байта (магия)
                                      │            проверки: размер / формат / дубликат
                                      │            rename tmp → captures/<sha256>.pcap[ng]
                                      │            запись в project.json: status = "indexing"
 202 {capture, jobId} ◄───────────────┤
                                      └──► jobs.Start("import_capture") ─► indexCapture ─► analyzeFile
                                                                                      │
        pcap.Reader.Next ─► netpkt.Decode ─► tcpflow.Assembler.Add   (по одному пакету)
                                                                                      │
        Assembler.Finish ─► []*tcpflow.Session ─► buildSession (DTO) ─► captureAnalysis
                                                                                      │
        indexCapture: status = "ready", слот анализа заполнен, linkActions, project.json сохранён
```

### 4.1. Приём файла и неизменяемое хранение

(`internal/server/routes.go`: `uploadCapture`, `uploadedFile`; `internal/app/captures.go`: `ImportCapture`, `storeUpload`)

1. HTTP-слой ограничивает тело `http.MaxBytesReader(MaxCaptureBytes + 1 МиБ)` и читает multipart **потоком**
   (`r.MultipartReader()`, поле `file`): файл не буферизуется целиком в памяти.
2. `storeUpload` создаёт временный файл `captures/.upload-*` и копирует тело в `io.MultiWriter(tmp, sha256, headWriter)`
   — за один проход получаются файл, SHA-256 и первые 4 байта. Источник ограничен `io.LimitReader(body, limit+1)`.
3. Проверки: размер > предела → `413 capture_too_large`; первые 4 байта — не сигнатура PCAP/PCAPNG
   (`captureMagic`: SHB `0a0d0d0a`, либо четыре варианта магии классического pcap в двух порядках байтов и двух
   разрешениях) → `422 unsupported_format`.
4. Под блокировкой проекта (`p.update`): запись с таким же SHA-256 уже есть → `409 duplicate_capture`; иначе
   `os.Rename(tmp → captures/<sha256>.pcap|pcapng)` и добавление `CaptureRecord` со статусом `indexing`.
   Проверка дубликата и переименование атомарны относительно других импортов того же проекта.
5. Имя файла для показа очищается (`cleanFileName`: без каталогов, без управляющих символов, ≤200 байт).

**Почему «content-addressed и неизменяемое».** Имя файла — его SHA-256; код нигде не открывает записи на запись и не
переименовывает их, кроме удаления при отмене незавершённого импорта. Поэтому `SourceRef.captureSha256` однозначно
называет байты, на которые ссылается любой результат (раздел 7). Дедупликация работает в пределах проекта.

После этого `ImportCapture` запускает задачу `import_capture` и сразу отвечает `202 Accepted` с `{capture, jobId}`;
интерфейс опрашивает `GET /jobs/{id}` (раздел 10).

### 4.2. Фоновая задача: `indexCapture` и `analyze`

`indexCapture` (`captures.go`) делает снимок записи и настроек проекта **под блокировкой**, затем выполняет тяжёлый
`analyzeFile` **без блокировки**, затем снова под блокировкой применяет результат. Если за время чтения файла
настройки проекта изменились (политики или целевые порты), анализ повторяется с новыми настройками, пока они не
перестанут меняться: повторный анализ после смены настроек (`UpdateProject`) пропускает записи в статусе `indexing`
(`TestSettingsChangedDuringIndexing`). Затем:

- успех → `applyAnalysis` (число пакетов, сессий, диагностика, время первого/последнего пакета), статус `ready`,
  `setAnalysis` (результат кладётся в кэш-слот), `linkActions` (действия журнала без связей привязываются к сессиям
  новой записи, 5.10), `p.rev++`, сохранение `project.json`;
- ошибка анализа → статус `error` + диагностика `analysis_failed`;
- отмена пользователем → файл и запись удаляются; остановка программы → всё остаётся, импорт продолжится при запуске.

`analyzeFile` (`internal/app/analysis.go`) оборачивает `analyze` в `recover`: паника в разборе превращается в ошибку
**этой записи** («внутренняя ошибка анализа»), процесс и другие записи не страдают.

`analyze` работает за **один последовательный проход** по файлу:

1. `os.Open`; файл читается через цепочку `bufio.Reader(1 МиБ) ← countingReader ← io.TeeReader(f, sha256)`: SHA-256
   считается на лету, а `countingReader` шлёт прогресс (чтение — первые 80% прогресса).
2. `pcap.NewReader(br)` определяет формат по магии.
3. Для каждого пакета: проверка отмены каждые 1024 пакета; обработка ошибок чтения (4.3); обновление времени
   первого/последнего пакета (пакеты без метки времени — Simple Packet Block — в эти границы не входят);
   `netpkt.Decode(pkt.LinkType, pkt.Data, pkt.OrigLen)`; при ошибке — учёт в `decodeErrs[code]` (счётчик и первые 10
   номеров пакетов), при успехе — `asm.Add(tcpflow.Input{Number, Timestamp, Seg})`.
4. После конца: `io.Copy(io.Discard, br)` дочитывает непрочитанный хвост, чтобы SHA-256 покрыл **весь** файл,
   даже если чтение остановилось раньше (предел пакетов, ошибка).
5. `asm.Finish()` собирает сессии; затем применяется предел `MaxSessions` (4.10); `buildSession` преобразует каждую
   `tcpflow.Session` в DTO (`TcpSession`, пакеты, `DirectedStream`).
6. Диагностика записи собирается в фиксированном порядке: ошибки чтения (`truncated_file`/`read_error`/`packet_limit`),
   `damaged_record`, ошибки декодирования по коду в алфавитном порядке, `session_limit`, сводка диагностик сессий по
   коду (коды — в 4.5); если SHA-256 файла ≠ записанному при импорте, в начало списка добавляется ошибка
   `integrity_mismatch`.

Данные пакета не удерживаются целиком: `tcpflow.Assembler.Add` копирует только **payload** в общие чанки по 1 МиБ
(`arena`), кадр после этого можно освобождать.

### 4.3. Чтение файла: `internal/pcap`

**Определение формата** (`reader.go`: `openReader`): первые 4 байта. `0a0d0d0a` — тип блока SHB pcapng; его
палиндромность делает определение независимым от порядка байтов. Иначе проверяются оба порядка на магию
`a1b2c3d4` (микросекунды) и `a1b23c4d` (наносекунды). Иное → `ErrUnknownFormat`.

**Классический PCAP** (`classic.go`):

| Что | Как |
|---|---|
| заголовок 24 байта | порядок байтов — по магии; принимается только версия 2.x; `thiszone` и `sigfigs` игнорируются |
| link type | `uint32 & 0xffff`: старшие 16 бит — длина FCS и зарезервированные биты, не тип канала (`TestClassicLinkTypeIgnoresFCSBits`) |
| время | секунды + доля; единица 1 мкс или 1 нс (по магии) — `time.Unix(sec, frac*unitNs)` |
| запись | 16-байтный заголовок; `OrigLen = max(origLen, capLen)` |

**PCAPNG** (`pcapng.go`), последовательность секций:

| Блок | Обработка |
|---|---|
| SHB (Section Header) | байтовый порядок секции — по `0x1a2b3c4d` (`detectByteOrder`); версия должна быть 1.x; **список интерфейсов секции сбрасывается** (`ng.section = ng.section[:0]`) |
| IDB (Interface Description) | link type, snaplen; опции `if_tsresol` (код 9) и `if_tsoffset` (код 14); по умолчанию разрешение 10⁻⁶ с. Каждый интерфейс получает сквозной номер в файле (`Packet.Interface`) |
| EPB (Enhanced Packet) | основной случай: ID интерфейса, 64-битная метка времени, captured/original length |
| SPB (Simple Packet) | интерфейс 0, **времени нет** (`time.Time{}`), длина захвата = min(orig, размер блока, snaplen) |
| OPB (устаревший Packet Block) | 16-битный ID интерфейса, остальное как EPB |
| NRB, ISB, custom, неизвестные | пропускаются |

Нюансы, которые стоит знать:

- **Точное время без плавающей точки** (`tsunit.go`): метка переводится в `time.Time` целочисленной арифметикой
  (`splitDecimal`, `splitBinary` через `bits.Mul64`), включая «двоичное» разрешение (старший бит `if_tsresol`) и
  смещение `if_tsoffset`. Тест `TestTsUnitConversionsAreExact`.
- **Несколько интерфейсов и секций:** `Reader.Interfaces()` возвращает все интерфейсы файла в порядке появления;
  каждый пакет несёт свой `LinkType`, и `analyze` декодирует его по нему. Интерфейс предыдущей секции в следующей
  не виден (`TestNgSectionsResetInterfaces`).
- **Граница между «пропустить пакет» и «файл кончился»:**
  - *Блок прочитан целиком, но пакет в нём непригоден* (EPB называет необъявленный интерфейс; `captured length` больше
    блока) → `*PacketError`: запись **потреблена**, `Next` можно вызывать дальше; номер пакета учитывается. В
    `analyze` это счётчик `damaged_record` (номера первых 10 пакетов).
  - *Нарушена структура блока* (длина не кратна 4 или < 12, длина > 256 МиБ, «хвостовая» длина ≠ ведущей) →
    `ErrCorrupt`: дальше читать нельзя, `analyze` пишет `read_error` («остаток файла не обработан»), прочитанное
    сохраняется.
  - *Файл оборван на середине записи* → `ErrTruncatedFile`: диагностика `truncated_file` (warning), последняя запись
    пропущена, всё прочитанное до неё используется.
- **Защита от ложных длин:** `readAnnounced` читает объявленное число байт кусками по 1 МиБ, так что повреждённое поле
  длины в коротком файле даёт `ErrTruncatedFile`, а не выделение гигабайтов (`TestDamagedLengthDoesNotAllocateAnnouncedSize`);
  длина записи сверх `maxRecordLen` (256 МиБ) — `ErrCorrupt`.
- Каждый `Packet.Data` принадлежит вызывающему (читатель его не переиспользует).

Поддерживаемые link types (`pcap/api.go`): `NULL(0)`, `EN10MB(1)`, `RAW(101)`, `LOOP(108)`, `LINUX_SLL(113)`, `IPV4(228)`,
`LINUX_SLL2(276)`. Остальные декодер отвергает с кодом `unsupported_linktype`.

### 4.4. Разбор кадров: `internal/netpkt`

`Decode(linkType, data, origLen)` возвращает `Segment` либо `*DecodeError` с кодом (он же код диагностики).
`wireLen = max(origLen, len(data))` — длина кадра «на проводе»; если `len(data) < wireLen`, кадр усечён snaplen.

| Уровень | Что делает `decode.go` |
|---|---|
| Ethernet II | 14 байт; **любое число VLAN-тегов** `0x8100`, `0x88a8`, `0x9100` (по 4 байта) снимается циклом; `EtherType < 0x0600` — кадр IEEE 802.3 (поле длины) → `non_ip`; `0x86dd` → `ipv6_unsupported`; ARP, LLDP и прочее → `non_ip` |
| Linux SLL / SLL2 | псевдозаголовок 16 / 20 байт, протокол в нём, дальше как EtherType |
| RAW / IPV4 | версия IP из старшего полубайта первого байта |
| NULL / LOOP | 4-байтное семейство адресов; для `NULL` порядок байтов хоста неизвестен, берётся меньшее из двух прочтений (семейства — малые числа); `AF_INET`=2 → IPv4; 10/24/28/30 (IPv6 разных ОС) → `ipv6_unsupported` |
| IPv4 | версия =4; **длина заголовка IHL×4 ≥ 20** — опции IP пропускаются по IHL, не разбираются; `total length` — граница сегмента |
| фрагменты | `MF` или ненулевое смещение (`frag & 0x3fff != 0`) → `ip_fragment`: **сборка фрагментов не реализована**, пакет пропускается |
| протокол | не TCP → `non_tcp` (UDP, ICMP, прочее) |
| TCP | длина сегмента ≥ 20; **data offset** ≥ 5 и ≤ длины; опции TCP пропускаются по data offset; флаги, окно, seq, ack |
| контрольная сумма | только если сегмент захвачен **целиком**: сумма по псевдозаголовку IPv4 + сегмент; корректна, если свёртка = `0xffff` (так принимаются оба нуля арифметики дополнения до единицы). Усечённый сегмент → `ChecksumUnknown` |

Три решения в IPv4, важные для защиты:

1. **Ethernet-дополнение не считается данными.** Граница payload — `total length` из заголовка IP, а не конец кадра:
   байты после неё — padding минимального кадра (60 байт) или FCS (`TestEthernetPaddingIsNotPayload`).
2. **`total length = 0`** трактуется как сегментация на стороне захвата (TSO/GSO): длина берётся из кадра, как это делает
   Wireshark (`TestSegmentationOffloadZeroLength`).
3. **Усечение snaplen** не ошибка: `Segment.Payload` содержит захваченные байты, `PayloadLen` — логическую длину из IP.
   Разница потом превращается в `Gap{reason: "truncated"}` (4.7). Если обрезан сам заголовок, код — `truncated_header`
   (а не `malformed`), потому что причина — snaplen (`frame.short`).

Контрольная сумма считается 64-битным накоплением по 32-битным словам с последующей сверткой (`onesSum`/`fold`):
это допустимо, потому что 2¹⁶ ≡ 1 (mod 0xffff). Контрольная сумма заголовка IPv4 **не проверяется**.

### 4.5. Диагностика неподдерживаемых и повреждённых данных

Ничего не пропускается молча: каждое пропущенное или неполное — это `Diagnostic{level, code, message, count,
packetNumbers}` записи (`Capture.Diagnostics`) или сессии (`TcpSession.Diagnostics`). Номера пакетов ограничены 10.

| Код | Уровень | Когда |
|---|---|---|
| `truncated_file` | warning | файл оборван посреди записи |
| `read_error` | error | нарушена структура файла; остаток не обработан |
| `damaged_record` | error | PCAPNG-блок пакета непригоден (интерфейс/длина), пакет пропущен, чтение продолжено |
| `packet_limit` | error | достигнут `MaxPackets`; анализ остановлен |
| `unsupported_linktype` | error | link type не из списка (в тексте названы типы) |
| `non_ip` / `non_tcp` | info | ARP/LLDP/802.3; UDP/ICMP |
| `ipv6_unsupported` | warning | IPv6 не поддерживается в основном сценарии |
| `ip_fragment` | warning | фрагмент IPv4 (без сборки) |
| `malformed` / `truncated_header` | warning | несогласованные заголовки / заголовок обрезан snaplen |
| `session_limit` | error | сессий больше `MaxSessions` |
| `tcp_gap`, `tcp_truncated`, `overlap_conflict`, `missing_handshake`, `checksum_offload`, `checksum_error`, `stream_too_large`, `reassembly_failed` | см. 4.7–4.10 | диагностика сессий; на уровне записи агрегируются по коду (`aggregateSessionDiagnostics`) |
| `integrity_mismatch` | error | SHA-256 файла не совпал с записанным |
| `analysis_failed` | error | анализ записи завершился ошибкой |

Эти сообщения видны пользователю в интерфейсе и в отчёте; выводы по записи с `integrity_mismatch` помечены как
недостоверные (раздел 7.3).

### 4.6. Сессии: ключ соединения, экземпляры, роли

`internal/tcpflow/assembler.go`, `session.go`.

**Ключ соединения.** `connKey` — *неупорядоченная* пара конечных точек `IP:порт` (`keyOf` упорядочивает их через
`netip.AddrPort.Compare`). Пакеты обоих направлений попадают в один ключ. Ключ не содержит интерфейса захвата.

**Экземпляры соединения (повторное использование 4-tuple).** На каждый ключ есть «текущий» (`current`) и «предыдущий»
(`previous`) экземпляр `conn`. Новый экземпляр открывается (`assembler.add` → `conn.opensNewInstance`), когда:

- приходит **SYN без ACK**, а текущий экземпляр уже закрыт (`FIN` с обеих сторон либо `RST`), либо у него был другой
  SYN (другой отправитель или другой `seq`), либо он начат без рукопожатия. Повторный SYN той же стороны с тем же `seq`
  — это ретрансмиссия SYN, экземпляр тот же (`acceptsSyn`). SYN, пойманный *после* SYN-ACK, который на него отвечает
  (`SYN.seq+1 == SYNACK.ack` от другой стороны), присоединяется к экземпляру (`TestLateSynJoinsTheInstance`);
- приходит **SYN-ACK**, которому текущий экземпляр не соответствует (`acceptsSynAck`): повторный SYN-ACK (тот же
  отправитель и `seq`) — свой; SYN-ACK на SYN этого экземпляра (с учётом данных в SYN, TCP Fast Open) — свой; у
  закрытого экземпляра без рукопожатия — новый. Экземпляру, начатому **без** рукопожатия, SYN-ACK принадлежит, только если
  его номера лежат чуть ниже уже увиденных (не дальше `1<<20`: SYN-ACK повторён сразу после рукопожатия, а увиденные
  сегменты продолжают его номера); иначе — **новый экземпляр**. Так обрабатывается случай, когда SYN нового соединения
  не попал в запись, а старое выглядит «открытым» (`TestPortReuseSynAckWhileOldInstanceOpen`).

**Запоздавшие сегменты вытесненного экземпляра.** Сегмент без SYN, чей `seq` лежит далеко от диапазона номеров текущего
экземпляра этого отправителя (`seqSpace.near`, зазор `spaceSlack = 1<<24`), но близко к диапазону *предыдущего*,
возвращаются в предыдущий (`assembler.add`, ветка `case !seg.Flags.Has(SYN) && …`). Иначе, например, повторно
отправленный FIN старого соединения превратился бы в «гигабайты потерянных байтов» нового
(`TestLateSegmentOfReplacedInstance`). Если номера нового экземпляра близки к старым (ISN по RFC 6528 идёт «чуть выше»
старого), запоздавший сегмент остаётся в новом экземпляре: он виден в списке его пакетов, а его номера обычно ложатся
перед началом нового потока, и байтов он не добавляет (комментарий в `assembler.add`; раздел 17).

**Роли клиента и сервера** (`builder.assignRoles`) и их достоверность (`TcpSession.Roles`):

| Источник | `Roles` | Как выбрана роль |
|---|---|---|
| захвачен SYN (без ACK) | `handshake` | клиент — отправитель SYN |
| нет SYN, есть SYN-ACK | `inferred` | клиент — получатель SYN-ACK |
| нет рукопожатия, ровно одна сторона использует целевой порт проекта | `inferred` | сервер — сторона с целевым портом |
| ничего не помогает (оба или ни один порт не целевой) | `unknown` | клиент — отправитель первого пакета |

Отсюда `startKnown`, `Handshake` и статус сессии (4.8). Роль «по умолчанию» — предположение, и оно маркируется как
`unknown`, а не выдаётся за установленное.

### 4.7. Сборка потока: относительные номера, арифметика по модулю 2³², алгоритм

**Относительные sequence numbers.** Для каждого направления вычисляется `base` — номер последовательности, которому
соответствует смещение 0 потока. Пакеты показываются с `Seq = seg.Seq − (base−1)` и `Ack = seg.Ack − (base_пира−1)`,
то есть «как в Wireshark»: SYN имеет `seq=0`, первый байт данных — `seq=1`. Зачем:

- смещение в потоке и `SourceRef` не зависят от случайного ISN, одни и те же байты имеют одни и те же координаты на
  любой машине и в любом отчёте;
- эксперт может сверить числа с Wireshark (`tcp.relative_seq`);
- внутри потока работают 64-битные смещения, а не 32-битные номера, которые «заворачиваются».

**Арифметика по модулю 2³²** (`internal/tcpflow/seq.go`, `seqUnwrapper`). Номер переводится в 64-битное смещение как
ближайшее к максимальному принятому: `at(seq) = high + int64(int32(seq − origin − uint32(high)))`. Знаковая разность
32-битных чисел — это сравнение номеров последовательности по модулю 2³², как принято в RFC 9293; поэтому
поток корректно проходит через 2³² (арифметика допускает и потоки длиннее 2 ГиБ; практический предел задают настройки, 4.10). «Опорная точка» `high` сдвигается только сегментами с
данными и FIN (`advance`); ACK и пустые сегменты читаются относительно неё (`at`). Тесты: `TestSeqUnwrapper`,
`TestSequenceWraparound`, а в `TestPropertyReassemblyOfIdenticalCopies` каждый пятый прогон начинается у границы 2³².

**Как определяется `base`** (`builder.findBases`, `estimateBases`):

1. есть SYN клиента → `base_c2s = synSeq+1`, `startKnown = true`;
2. нет SYN, но есть SYN-ACK сервера → `base_c2s = SYN-ACK.ack` (подтверждает ISN+1), `base_s2c = SYN-ACK.seq+1`; оба `startKnown`;
3. иначе — **оценка** (`estimateBases`): самый ранний номер, несущий payload или FIN (первый увиденный байт); при
   отсутствии данных — наибольший номер пустых сегментов; при отсутствии и их — наименьший подтверждённый пиром. Такой
   поток помечается `startKnown = false`: **смещение 0 — просто первый увиденный байт**, а не начало соединения.
   Keep-alive-пробы (≤1 байт, целиком ниже уже использованного отправителем или подтверждённого пиром), номер `RST` (его `ack` учитывается) и
   сегменты с повреждённой суммой (`suspect`, 4.9) в оценке не участвуют.

**Длина потока** (`half.finishExtent`) — максимум из конца самого дальнего payload (включая обрезанные хвосты), позиции
FIN и **подтверждённого пиром** положения (ACK). Последнее даёт «хвостовые пропуски»: если сервер подтвердил байты,
которых нет в записи, они остаются пропуском, а не исчезают. Длина ограничена пределами (4.10).

**Размещение сегментов** (`half.place`, `stream.go`). Принятые диапазоны хранятся как упорядоченный список непересекающихся
`span{start, end, owner, rivals, weak}`: `owner` — пакет, чьи байты лежат в потоке, `rivals` — пакеты с *другими* байтами
для того же диапазона. Для нового сегмента:

1. **Быстрый путь:** если он начинается за концом всего принятого — байты копируются, диапазон добавляется.
2. **Общий путь:** находятся перекрывающиеся диапазоны; непокрытые части копируются (`fill`), перекрытые сравниваются
   побайтно (`compare`):
   - байты **равны** → это дубликат; диапазон остаётся, ничего не меняется;
   - байты **различаются** → *конфликт*: победитель определяется политикой перекрытий проекта `first` (остаётся
     ранее захваченный пакет) или `last` (побеждает последний). Побеждённые пакеты записываются в `rivals`, а потом
     превращаются в `Conflict{offset, length, packets, chosen}`; сравнение идёт по прогонам, поэтому два разных
     участка внутри одного перекрытия дают два `Conflict`, но одну диагностику.
3. Разметка пакета (`half.accept`):
   - `retransmission` — **все** номера последовательности пакета уже были: он не добавил ни новых байтов, ни нового
     усечённого хвоста и его конец не дальше `next`; чистый ACK ретрансмиссией не бывает;
   - `out_of_order` — пакет принёс новые байты *ниже* уже принятого максимума (заполнил «дыру»);
   - `overlap_conflict` — часть байтов отличалась от уже принятых;
   - `truncated` — пакет усечён snaplen; `checksum_warning` — неверная контрольная сумма;
   - `keep_alive` — проба на `SND.NXT−1` с ≤1 байтом: не размещается и не сравнивается.
4. Данные в **RST** никогда не попадают в поток (это диагностический текст); RST не расширяет поток.
5. `StreamOffset` пакета — смещение его payload в потоке, либо `-1`, если пакет ничего не внёс (чистый дубликат).

**Отличие ретрансмиссии от конфликта — только содержимое**: те же номера и те же байты → `retransmission`;
те же номера и другие байты → `overlap_conflict` (и тоже обычно `retransmission`: все номера уже были). Политика
перекрытий выбирает, чьи байты оставить; **оба варианта всегда видны** в `Conflict.Packets`.

**Пропуски** (`half.gaps`): все диапазоны `[0, length)`, не покрытые принятыми байтами. Причина:

| `reason` | Когда |
|---|---|
| `truncated` | диапазон объявлен усечённым пакетом (IP-длина больше захваченного), но его байтов нет |
| `lost` | всё остальное: на стороне захвата не видно ни этих байтов, ни усечённого пакета с ними |

Других причин нет ни в коде, ни в API (`model.GapLost`, `model.GapTruncated`; так же и в типах фронтенда): «начало не
захвачено» выражается не пропуском, а признаком `startKnown=false` (смещение 0 — первый увиденный байт). Байты
пропуска в `Stream.Data` — нули **только как транспорт**; неизвестность несёт список `Gaps` (раздел 5.7).

Для крупных записей диагностик пропусков не больше 20 на направление и причину; остаток сводится в одну запись со
счётчиком (`maxGapDiagnostics`, `TestManyGapsAreSummarised`).

### 4.8. Статус сессии

`builder.status` (`diag.go`):

| Статус | Условие |
|---|---|
| `error` | поток обрезан пределом размера (`stream_too_large`) или сборка соединения упала (`reassembly_failed`, 4.10) |
| `partial` | есть пропуски или конфликты; либо байты принял только повреждённый пакет без подтверждения целым; либо рукопожатие не захвачено или соединение не закрыто |
| `complete` | захвачены SYN клиента **и** закрытие (FIN с двух сторон либо RST), нет пропусков и конфликтов |

Закрытие и рукопожатие обязательны для `complete` намеренно: соединение, у которого не видно начала или конца, нельзя
называть полным.

### 4.9. Контрольные суммы: offloading и реальное повреждение

(`tcpflow/api.go` — политика; `session.go` — `builder.suspect`, `countChecksums`; `stream.go` — `compare`)

Политика проекта `checksumPolicy`:

- `ignore` — суммы вообще не смотрятся (в `assembler.add` статус `Bad` заменяется на `OK`);
- `warn` (по умолчанию) — пакеты с неверной суммой получают флаг `checksum_warning`, а дальше работает правило
  **большинства по направлению**:
  - если у отправителя неверны **почти все** пакеты (число проверенных верных ≤ числа неверных), это **checksum
    offloading** на узле захвата: сумма ещё не посчитана сетевой картой в момент записи. Данные используются как есть,
    ничего не меняется, диагностика `checksum_offload` (info) со счётчиком и первыми номерами;
  - если неверна сумма у **отдельных** пакетов среди верных (верных строго больше), пакет считается повреждённым
    (`suspect`): его `seq`/`ack` **не расширяют поток** и не двигают опорную точку; при расхождении байтов с
    пакетом с верной суммой побеждает верный **независимо от политики перекрытий**; диагностика `checksum_error`
    (warning). Если копия с верной суммой не пришла, байты повреждённого пакета остаются в потоке, но сессия получает
    `partial` («байты не проверены»).

Таким образом, offloading (системное явление на узле захвата, поэтому данные нормальны) и реальное повреждение
(единичные пакеты) различаются *статистически по каждому направлению*, а не по отдельному пакету. Тесты:
`TestChecksumOffload`, `TestChecksumOffloadVersusCorruption`, `TestStrayPacketsDoNotInflateTheStream`.

### 4.10. Защитные пределы и изоляция ошибок

| Что | Предел | Что происходит при превышении |
|---|---|---|
| `MaxStreamBytes` (по умолч. 64 МиБ) | длина одного направления | поток обрезается на пределе, `stream_too_large` (error), статус сессии `error` |
| `MaxTotalBytes` (по умолч. 1 ГиБ) | все направления записи вместе | сессии собираются в порядке первого пакета; направление, не поместившееся в остаток, обрезается; та же диагностика |
| `MaxPackets` (2 000 000) | пакеты записи | `packet_limit`, прочитанное доступно |
| `MaxSessions` (20 000) | сессии записи | остаются первые, `session_limit` с общим числом |

Нужны потому, что **размер потока определяется номерами последовательности, а не захваченными байтами**: байты пропусков
хранятся нулями, и один пакет с далёким `seq` без этих пределов потребовал бы гигабайты (`TestTotalStreamBudget`).
Помимо пределов, два механизма не дают такому номеру попасть в поток: повреждённые пакеты не расширяют его (4.9), а
запоздавшие сегменты вытесненного экземпляра возвращаются в свой экземпляр (4.6).

**Изоляция:** `safeBuild` (`assembler.go`) ловит панику при сборке *одной* сессии и возвращает её со статусом `error`,
диагностикой `reassembly_failed`, сохранёнными пакетами и пустыми потоками; остальные сессии не затронуты
(`TestOneFailingSessionDoesNotBreakTheOthers`). Выше стоит `analyzeFile` с `recover` на запись целиком.

### 4.11. Разобранный пример

Клиент отправляет 20 байт `AAAA BBBB CCCC DDDD EEEE` (пять сегментов по 4 байта); ISN клиента — 1000, рукопожатие захвачено.
Пакет с `DDDD` потерян, `BBBB` пришёл позже `CCCC`, `AAAA` продублирован, а повтор `CCCC` пришёл с другими байтами
`CCXX`. Номера пакетов — номера в записи, `seq` — относительный (как в API).

| № | Направление | Флаги | seq | Данные | Что делает сборка | Пометки пакета |
|---|---|---|---|---|---|---|
| 1–3 | c2s/s2c/c2s | SYN, SYN-ACK, ACK | — | — | `base_c2s = 1001`; `roles = handshake`; `startKnown = true` | — |
| 4 | c2s | PSH,ACK | 1 | `AAAA` | в потоке `[0,4)` | — |
| 5 | c2s | PSH,ACK | 9 | `CCCC` | в потоке `[8,12)`; между ними `[4,8)` пока не заполнено | — |
| 6 | c2s | PSH,ACK | 1 | `AAAA` | байты равны, ничего не добавлено | `retransmission`, смещение `-1` |
| 7 | c2s | PSH,ACK | 5 | `BBBB` | заполняет `[4,8)` ниже принятого максимума | `out_of_order` |
| 8 | c2s | PSH,ACK | 9 | `CCXX` | на `[10,12)` байты отличаются от пакета 5 | `retransmission`, `overlap_conflict` |
| 9 | c2s | PSH,ACK | 17 | `EEEE` | в потоке `[16,20)`; `[12,16)` остаётся неизвестным | — |
| 10 | s2c | ACK | 1 | — | подтверждает первые 12 байт (`ack=13`) | — |
| 11–13 | c2s/s2c/c2s | FIN,ACK · FIN,ACK · ACK | | | соединение закрыто, длина потока 20 | — |

Результат, снятый с работающего кода (`go test` на тех же последовательностях):

```text
политика first:  Data = "AAAABBBBCCCC" + 00 00 00 00 + "EEEE"
                 Gaps      = [{offset 12, length 4, reason lost}]
                 Conflicts = [{offset 10, length 2, packets [5 8], chosen 5}]
                 пакет 8: смещение -1 (ничего не добавил)
политика last:   Data = "AAAABBBBCCXX" + 00 00 00 00 + "EEEE"
                 Conflicts = [{offset 10, length 2, packets [5 8], chosen 8}]
                 пакет 8: смещение 8 (его байты победили)
статус сессии:   partial  (есть и пропуск, и конфликт)
диагностики:     tcp_gap (warning)          «C→S: 4 Б неизвестны на смещении 0xC (потерян сегмент)»
                 overlap_conflict (error)   «C→S: повторная передача с другими байтами (2 Б), использован пакет #5»
```

Четыре нуля на `[12,16)` не данные: движок получит диапазон `Gap{12, 4}` и не станет трактовать их как значения.

## 5. Движок интерпретаций

Вход движка (`internal/engine/api.go`) — `SessionInput`: метаданные сессии, по одному `StreamInput` на направление
(байты, список пропусков `Gaps`, список сегментов `Segments` с номерами пакетов и временем, признак
`UnknownStart`) и **действия журнала, привязанные к сессии**. Выход `ParseSession` — `ParsedSession{Messages, Unframed}`;
выход `Verify` — `Result{Summary, Findings}`. Движок чистый: ни диска, ни сети, ни часов.

`app.engineInput` (`internal/app/messages.go`) собирает этот вход из результата `tcpflow`: байты потока, пропуски,
сегменты, `UnknownStart = !StartKnown`.

### 5.1. Формат `protolab/v1` и его проверка

Полное описание формата — `docs/interpretation-format.md`. Типы лежат в `internal/spec/spec.go` (`Spec`, `Framing`,
`MessageRule`, `FieldRule`, `Assertion`).

Проверка (`spec.Parse`) двухступенчатая:

1. **Строгое декодирование** (`Decode`): `json.Decoder` с `DisallowUnknownFields`, затем требуется, чтобы после объекта
   не было данных (`dec.Token()` должен вернуть `io.EOF`). Ошибки декодирования `encoding/json` не содержат пути с
   индексами, поэтому `decodeIssue` повторно проходит документ потоково по структуре `Spec` (`schemaWalker`) и
   выдаёт **точный путь** вида `$.messages[0].fields[1].scale` и понятное сообщение («Неизвестное поле», «Ожидается
   число»…). Синтаксические ошибки получают строку и столбец. Ключи сопоставляются как в `encoding/json` (точное
   совпадение, затем без учёта регистра).
2. **Семантика** (`validate`): допустимые `kind` и параметры кадрирования (для `length_prefixed` обязательны
   `lengthField` и `lengthAdjust`); `direction` ∈ `c2s|s2c|any`; корректный hex
   (`ParseHex` принимает `A5 01`, `a501`, `0xA5, 0x01`, `A5:01`); неотрицательные `offset` у `match`; **ссылки
   `count`/`length` только на предыдущее целочисленное поле того же уровня**; `itemSize > 0`; `checksum` ∈ `sum8|xor8`;
   `status` ∈ `structural|hypothesis|confirmed`; `format` ровно `protolab/v1`; уникальность `id` правил и имён полей
   уровня; `assertions[].rule` существует, `checks[].equals` вида `params.<имя>` / `observed.<имя>`. Отсутствие
   `offset` у поля ловится отдельно (`missingOffsets` по сырому JSON: в структуре «нет ключа» и `0` неотличимы).
   Предупреждения (не блокируют): нет имени протокола, нет правил, правило без `match`, `length_prefixed` без `sync`.

Невалидную спецификацию нельзя сохранить как версию (`app.checkSpec` → `422 invalid_spec`, `details` — список
`Issue`) и нельзя запустить в проверке. Эндпоинт `POST /interpretations/validate` на корректный JSON-запрос всегда
отвечает `200` со списком замечаний.

Скачанный файл версии (`/export`, артефакт отчёта) несёт служебный объект `$meta` (5.2), который строгий разбор отверг
бы как неизвестное поле. Поэтому API (`validate`, создание интерпретации и версии, `preview`) сначала удаляет `$meta`
из корня (`withoutMeta` → `report.StripMeta`), так же как `protolab apply`/`verify` (`loadSpec`): экспортированный
файл можно вставить в редактор этого или другого проекта (`TestExportedSpecFileIsAccepted`).

### 5.2. Канонический JSON, хеш и неизменяемость версий

`spec.Hash(s)` = SHA-256 от `json.Marshal(*Spec)` (`internal/spec/spec.go`). Каноничность обеспечивает сама
сериализация: поля структур идут в порядке объявления, ключи отображений (`enum`) сортируются, пробелов нет,
значения по умолчанию отбрасываются тегами `omitempty`; `Length` сериализуется отдельным методом (`число` или `имя поля`).
Обязательные списки без `omitempty` — `messages`, `match` и `fields` правила, `checks` утверждения — `Decode`
нормализует (`Spec.Normalize`): пропущенный ключ и `null` становятся `[]`, поэтому пропущенный и пустой список дают
один и тот же канонический вид без `null` (`TestParseNormalizesOmittedLists`). Поэтому **хеш не зависит от
пробелов, порядка и регистра ключей во входном JSON** — только от содержания.

Что это даёт:

- Версия интерпретации — запись `InterpretationVersion{ID, Version, Hash, Comment, ParentVersionID, Spec}`. API умеет
  только **добавлять** версии (`POST /interpretations/{id}/versions`); редактирования и удаления версии нет.
  Если хеш новой спецификации равен хешу последней версии — `409 no_changes` (`addVersion`).
- Проверка (`VerificationRun`) хранит `versionId`, `version`, `versionHash`, `corpusHash`, настройки и версию движка:
  результат всегда можно привязать к точной спецификации.
- Экспортированный файл спецификации и отчёт содержат хеш (`$meta.hash`, `examples.specHash`); `protolab verify`
  пересчитывает хеш по файлу и предупреждает о расхождении.

Оговорка: хеш **не пересчитывается при загрузке проекта**; неизменяемость обеспечивается отсутствием операций
изменения в API и проверяется там, где хеш сверяют (`verify`, отчёт), но не навязывается криптографически при чтении
`project.json`. Версии, сохранённые до появления нормализации, могли содержать `null` в этих списках: при загрузке
`normalizeState` (`internal/app/project.go`) приводит их к `[]`, чтобы API не отдавал `null`, а записанный хеш
оставляет прежним (он был посчитан по старому виду).

### 5.3. Компиляция

`compile` (`internal/engine/compile.go`) вызывается один раз на `ParseSession`/`Verify` и готовит всё, что не должно
повторяться на каждое сообщение: hex-шаблоны переведены в байты; для `length_prefixed` вычислены `minLen`
(по умолчанию `lengthField.offset + size`, но не меньше 1 — сообщение нулевой длины не продвигало бы разбор) и `maxLen`
(по умолчанию `DefaultMaxLength = 65 536 + 64`); ширины целых; ключи `enum` переведены в `int64` (ключ совпадает только с
десятичной записью значения: `"01"` и `"1.0"` ничему не равны); для каждой ссылки `count`/`length` собран список
предшествующих целых полей; число десятичных знаков для `scale` (`scaleDecimals`); утверждения сгруппированы по
правилам. Поле неизвестного типа получает `kindInvalid` и при разборе даёт нарушение «Неизвестный тип».

### 5.4. Кадрирование

(`internal/engine/frame.go`, `stream.go`) Граница TCP-сегмента **не** граница сообщения: кадрирование работает по
восстановленному потоку направления. Инвариант (`frameStream`): **каждый известный байт потока попадает ровно в один
кадр либо в один «вне сообщений» диапазон** (`Unframed`); байты пропусков вне кадров относятся к дефектам записи
(`TestFramingAccountsForEveryKnownByte`).

**`length_prefixed`** (`frameLengthPrefixed`), цикл по позиции `pos`:

1. Если начало потока неизвестно (`UnknownStart`) — смещение 0 не граница сообщения: сначала ищется `sync`.
2. Если `sync` нужен, `findSync` ищет шаблон **только на известных байтах**; не найден — остаток потока «вне
   сообщений». Без `sync` в спецификации поиск вырождается в «начать прямо здесь», то есть в перебор по байту.
3. Заголовок длиннее остатка потока → частичный кадр «Поток закончился внутри заголовка», конец.
4. **Если в заголовке до конца поля длины (`[pos, pos+offset+size)`) есть пропуск, длина неизвестна, и граница
   сообщения ненадёжна**: байт `pos` (если он известен) идёт «вне сообщений», позиция сдвигается на следующий
   известный байт (`skipUnknown`), включается поиск `sync`, который сам перешагивает неизвестные байты.
5. Полная длина = `значение поля + lengthAdjust` (с насыщением, без переполнения). Вне `[minLength, maxLength]` —
   один байт «вне сообщений» и поиск `sync` дальше (или следующий байт).
6. Объявленная длина больше остатка потока → частичный кадр «Ожидалось N Б, в потоке M Б», конец.
7. Иначе кадр `[pos, pos+total)` и переход вперёд.

**Пропуск внутри тела** кадра не сбивает разбор: длина известна из заголовка, а номера последовательности TCP
дают точный размер пропуска, поэтому следующий кадр начинается там, где ему положено; кадр получает статус `partial`
и пометку «N Б неизвестны (пропуск в записи)». **Пропуск, накрывший заголовок**, приводит к повторной
синхронизации по `sync` уже после пропуска; байты между пропуском и найденным шаблоном остаются «вне сообщений»
(`TestLostSegmentResynchronises`: сообщение 1 `ok`, сообщение 2 `partial`, 3 байта «вне сообщений», сообщение 4 `ok`).

**`delimiter`** (`frameDelimited`): сообщение заканчивается после каждого разделителя, найденного на известных байтах;
поиск не перекрывается (`00 00` в `00 00 00` — одно совпадение); хвост без разделителя — частичный кадр «Нет
завершающего разделителя»; при неизвестном начале первый кадр получает «Начало сообщения не захвачено» и статус
`partial`. `sync` при `delimiter` не используется. **`fixed`** — куски по `size`, последний неполный — частичный
(«Поток закончился внутри сообщения»); неизвестное начало `fixed` не учитывает.

Общая развязка в `emit`: **кадр, целиком состоящий из неизвестных байтов, не создаётся** (в нём нечего
интерпретировать), а кадр с хотя бы одним неизвестным байтом получает `partial`.

**Предел числа сообщений.** `SessionInput.MaxMessages` (в `app` — `Limits.MaxMessages`, 200 000) ограничивает
`ParseSession` *до* разбора: `emit` перестаёт записывать кадры после `MaxMessages + 1` на направление, и если кадров
больше предела, сессия не строится — `ParsedSession.TooMany`, списки пустые. Иначе кадрирование, режущее длинный
поток на байты, создало бы миллионы сообщений раньше любой проверки. `app` превращает `TooMany` в
`422 message_limit` для сообщений сессии, черновика (`preview`) и сравнения по проекту (там 422 и при сумме больше
предела); текст ошибки называет предел, но не фактическое число (`TestParseSessionMaxMessages`,
`TestMessageLimitIsCheckedBeforeParsing`). `Verify` предел не применяет (сообщения там не накапливаются, 6.3), `apply`
его не задаёт.

Порядок сообщений (`timeOrder`): оба направления сливаются по времени сегмента, содержащего первый байт сообщения
(`segmentIndex.at`); при равном времени — по смещению в потоке, при равенстве и его — клиент раньше сервера
(устойчивое слияние c2s, затем s2c). Если байт ни в одном сегменте не
захвачен, берётся время последнего сегмента. Список номеров пакетов сообщения — все сегменты, пересекающие его диапазон.

### 5.5. Сопоставление правил

(`session.go`: `matchRules`, `rule.matches`; `builder.build`) Проверяются **все** правила; кандидатом правило является,
если подходит по направлению (`c2s`/`s2c`; `any` или пусто — любое) и **все** условия `match` выполнены:
`offset ≥ 0`, шаблон целиком помещается в сообщение, **ни один байт шаблона не неизвестен** (нулевой заполнитель
пропуска никогда не «совпадёт» с шаблоном `00`) и байты равны.

| Число кандидатов | Результат |
|---|---|
| 0 | `unknown_type` (сообщение без правила) |
| 1 | разбор по правилу |
| >1 | разбор идёт **по первому** правилу в порядке спецификации; `candidateRuleIds` перечисляет все; в `issues` добавляется «Подходят правила: …»; статус `ambiguous` |

Неоднозначность — результат, а не ошибка: проверка сообщает о ней находкой и счётчиком, а не прячет.

### 5.6. Поля

(`internal/engine/fields.go`, `fieldParser`) Поддерживаются типы `u8 i8 u16 i16 u32 i32` (порядок `le` по умолчанию
или `be`), `bytes`, `ascii`, `array`.

- **Смещения.** Положительные — от начала сообщения (для элементов массива — от начала элемента); **отрицательные
  всегда от конца сообщения** (`-1` — последний байт). Поле, выходящее за границы сообщения, — нарушение «Поле
  выходит за границы сообщения» (и его байты не считаются покрытыми).
- **Длина из другого поля.** `length`/`count` могут быть числом или именем ранее разобранного целого поля **того же
  уровня** (так требует и проверка 5.1). Значения лежат в стеке кадров — по кадру на уровень вложенности; ссылка
  разрешается в своём кадре: побеждает ближайшее предшествующее целое поле с этим именем, получившее значение.
  Неразрешённая ссылка (поле вне сообщения или в пропуске) даёт `0`.
- **Массивы.** Размер = `count × itemSize` (с насыщением); элементы получают пути `entries[3]`, поля внутри — `entries[3].value`;
  нарушение в элементе помечает и элемент, и массив. Без положительного `itemSize` и при `count > 0` — нарушение.
- **Отображение.** `scale` (отображаемое значение = raw × scale, с округлением до числа знаков масштаба), `unit`,
  `enum` (подпись + исходное число). Числа форматируются по правилам JavaScript (`jsNumber`, `roundFixed`,
  `isTie`): это сознательно, чтобы вывод совпадал с эталонной реализацией на TypeScript (5.12).
- **Проверки** (результат — `status: violation` и текст в `issue`): значение вне `enum`; `expect` (`equals`, `min`, `max`,
  `oneOf` — по **исходному** значению, сообщается первое нарушенное условие); `checksum` — `sum8` или `xor8` по байтам
  сообщения `[0, offset)`. При нескольких нарушениях у поля остаётся текст последней проверки.
- **Значения:** целые — `int64`, `bytes` — шестнадцатеричная строка, `ascii` — печатные символы как есть, остальные `.`.
- Арифметика смещений и размеров насыщающая (`addSat`, `mulSat`, `clampInt`): враждебные значения в спецификации не
  приводят к переполнению (`TestAdversarialSpecValues`).

### 5.7. Неизвестные байты никогда не читаются как нули

Один и тот же принцип проведён через все уровни:

| Уровень | Где | Что гарантировано |
|---|---|---|
| сборка | `tcpflow.half.gaps`; `app.engineInput` | пропуск описан диапазоном `Gap`; список передаётся движку вместе с байтами |
| маска | `engine.unknownMask` | по `Gaps` строится маска «1 = неизвестный байт» (нет пропусков — маски нет) |
| кадрирование | `findSync`, `frameDelimited`, `frameLengthPrefixed`, `emit` | `sync` и разделитель не совпадают на неизвестных байтах; поле длины в пропуске не читается; кадр из одних неизвестных байтов не создаётся |
| правила | `rule.matches` | условие `match` не выполняется на неизвестном байте |
| поля | `fieldParser.parseField` | поле, задевающее хотя бы один неизвестный байт: `status: "unknown"`, `value: null`, `display: "??"`, текст «Байты поля неизвестны (пропуск в записи)» |
| контрольные суммы | `fieldParser.checksumIssue` | если среди `[0, offset)` есть неизвестный байт, сумма **не проверяется** (иначе несоответствие обвиняло бы протокол в дефекте записи) |
| находки | `tally.captureDefects`, `tally.message` | пропуски записи — отдельные находки `capture_defect`; сообщение с неизвестными байтами получает `partial`, а не `ok` |
| наблюдения | `project.snapshot` | в снимке неизвестные байты записываются как `??`, а не `00` |

Дополнительно у каждого сообщения есть `Message.Unknown` — **диапазоны байтов сообщения, не объяснённые ни одним
полем** (`appendUncovered` по маске `covered`). Это не то же самое, что пропуск записи: это «границы известного» в
частичной интерпретации. Неизвестное поле «заняло» свои байты (они покрыты), но не декодировано.

Нюансы, которые полезно знать заранее (они выяснены экспериментом на коде):

- если сам **байт-счётчик или длина** (на которые ссылается другое поле) лежит в пропуске, зависимое поле видит
  «нераспознанную ссылку = 0» и получается пустым (`length: 0`, `status: ok`), а настоящие его байты остаются в
  `Message.Unknown`; сообщение при этом `partial`. нулевой «заполнитель» из пропуска не становится значением ни одного поля;
- поле контрольной суммы, не проверенной из-за пропуска, остаётся `ok` (нарушения не найдено), но **не** «подтверждено».

### 5.8. Статусы сообщения

| Статус | Когда (в порядке приоритета, `builder.build`) |
|---|---|
| `unknown_type` | ни одно правило не подошло |
| `partial` | кадр оборван концом потока, содержит неизвестные байты или (у `delimiter`) не имеет захваченного начала |
| `ambiguous` | подошло более одного правила |
| `violation` | у любого поля (в том числе вложенного) статус `violation` |
| `ok` | иначе |

Приоритет проверяется тестом `TestStatusPrecedence`: частичное сообщение остаётся частичным, даже если у него есть
нарушение или двусмысленность, но нарушения полей всё равно попадают в находки проверки.

### 5.9. Статусы смысла: структура, гипотеза, подтверждено

Каждое поле несёт `meaningStatus` (`ParsedField.MeaningStatus`), который задаёт **исследователь** в спецификации:

| Значение | Смысл |
|---|---|
| `structural` | структура подтверждается правилами (поле есть, тип, ожидания), но смысл не утверждается |
| `hypothesis` | смысл — предположение, опирается на гипотезу (`hypothesis` — её id) |
| `confirmed` | смысл подтверждён исследователем |

Если `status` не указан, действует вычисленное значение `spec.EffectiveMeaningStatus` (`internal/spec/spec.go`): есть
`meaning` — `hypothesis`, иначе `structural`. Одну и ту же функцию используют движок (`ParsedField.MeaningStatus`),
отчёт (колонка «Основание») и интерфейс, так что основание поля везде одно (`TestReportShowsEffectiveMeaningStatus`).

**Движок никогда сам не присваивает `confirmed`.** Успешный разбор (`status: ok`) означает лишь, что байты согласуются
со структурой и ожиданиями. В демо-интерпретации ThermoLink v3 поле `checksum` с `sum8` проверяется на каждом
сообщении, но остаётся `status: hypothesis` со ссылкой на гипотезу h-05 сценария демо (в проекте у неё случайный id
`hyp-…`): совпадение суммы подтверждает алгоритм на этих примерах, а не «смысл». Отчёт тоже напоминает об этом: в нём
есть строка «Совпадение на выбранных примерах не доказывает назначение полей и универсальность модели» и раздел
«Открытые вопросы» (`report.Markdown`). В открытые вопросы попадают гипотезы в статусах `proposed`/`testing`, поля со
смыслом при основании `structural` («структура описана, назначение не подтверждено») и поля с основанием `hypothesis`
без ссылки на гипотезу («назначение … предполагается, гипотеза с основаниями не указана»).

### 5.10. Утверждения по журналу действий

(`internal/engine/assert.go`, `internal/app/actions.go`)

**Журнал** — это действия исследователя в штатном клиенте (`ActionEntry`: время, вид, параметры `params`, наблюдаемое
`observed`). Его можно ввести вручную или импортировать из CSV/JSON: ошибка в любой записи отклоняет файл целиком
(`422 invalid_action_log`). Файл больше 16 МиБ (`maxActionLogBytes`; читается на байт больше, HTTP-предел тела —
17 МиБ) отклоняется целиком с `413 action_log_too_large`, а не обрезается (`TestImportActionsRefusesOversizedLog`).

**Привязка действий к сессиям по времени** (`autoLink`): среди *целевых* сессий выбирается та, что **началась в окне от
0,5 с до действия до 5 с после него**, и из них — ближайшая по модулю разницы (`links[].method = "auto_time"`,
`deltaMs` = начало сессии − время действия). Окно — константы `linkBefore`, `linkAfter`. Вручную сессии задаются при
создании действия (`method = "manual"`); при импорте журнала заданные в файле сессии игнорируются — только время.
Время начала сессии — самый ранний пакет сессии. Если журнал импортирован раньше записи, действия, у которых нет ни одной
связи, привязываются тем же окном к сессиям новой записи, когда её индексация завершается (`linkActions` в
`indexCapture`, `TestActionsLinkedAfterCaptureImport`). Уже существующие связи не пересматриваются.

**Применение** (`bindAssertions`, `applyAssertions`): для правила, по которому разобрано сообщение, берутся его
утверждения; для каждого берётся **первое привязанное к сессии действие нужного вида** (`actionKind`). Каждая проверка
`{field, equals: "params.paramId"}` читает ожидаемое число из действия (`toNumber`: число JSON или числовая строка,
`" -5.5 "`, `"0x15"`; пустая строка, `null`, логические значения числами не считаются, и такая проверка пропускается).
Значение **верхнеуровневого** поля берётся с учётом `scale` и сравнивается с допуском `1e-6`. Несовпадение — нарушение
этого поля с текстом «`88 ≠ params.value = 600 (действие «…», проверка a-set-value)`»; поле неизвестное (пропуск) не
проверяется.

Такое нарушение — не абстрактная ошибка разбора, а **контрпример к гипотезе**: оно попадает в находки проверки с
точными байтами в примерах, из них собираются контрпримеры гипотезы (`Hypothesis.Counterexamples`, `Counterexample.RunID`).
В демо именно так находится ошибка v1: поле `value` шириной 1 байт даёт `88` вместо `600` (600 mod 256). Проверка v1
на расширенном корпусе фиксирует 3 нарушения: два — у `set_param_req.value`, одно — у `get_measurement_resp.temperature`
(беззнаковое чтение даёт `6548.1` вместо `-5.5`); v2/v3 их не имеют (`TestDemoProjectEndToEnd`).

### 5.11. Пример разбора

Сообщение `set_param_req` ThermoLink v3 (`A5 | type | seq | len(u16 LE) | payload | sum8`): `A5 02 08 03 00 01 C8 00 7B`.

| Сценарий | Результат |
|---|---|
| все байты известны | статус `ok`; `param_id = 1` → «уставка (1)»; `value = 200` (`i16 le`); `checksum = 123`, `meaningStatus: hypothesis` |
| последний байт изменён | статус `violation`: поле `checksum`, issue «Контрольная сумма sum8: ожидалось 0x7B» |
| в пропуске байты 6–7 (поле `value`) | статус `partial`; `value`: `status: unknown`, `value: null`, `display: "??"`; `issues: ["2 Б неизвестны (пропуск в записи)"]`; остальные поля прочитаны; `checksum` не проверена |

### 5.12. Версия движка и эталонная реализация

`engine.Version = "protolab-engine/1.1"` записывается в каждый запуск проверки (`VerificationRun.engineVersion`) и в файл
примеров; `protolab verify` предупреждает, если версия отличается. Версия 1.1 — «кадрирование сначала синхронизируется,
если начало соединения не захвачено».

Движок сверяется с **эталонной реализацией на TypeScript** (`frontend/src/mocks/engine`, она используется в mock-режиме
интерфейса): тест `TestMatchesReferenceImplementation` сравнивает JSON сообщений и сводок проверки на демо-корпусе
(данные и ожидания в `internal/engine/testdata/reference.json.gz`). Сознательные отличия, записанные в комментарии
теста: контрольная сумма не проверяется по пропускам (эталон складывает нулевой заполнитель и даёт ложное нарушение),
неизвестные байты никогда не совпадают с шаблонами и разделителями, номера пакетов в примерах отсортированы.

## 6. Проверка (verification)

### 6.1. Корпус и его хеш

`CreateCorpus` (`internal/app/verification.go`) принимает название, список сессий и фильтр (фильтр хранится для
интерфейса). Список сортируется, дубликаты убираются, каждая сессия должна существовать. **Хеш корпуса**
(`corpusHash`) — SHA-256 по строкам `<sessionId>:<sha256 записи>\n` в отсортированном порядке: те же идентификаторы
сессий поверх других байтов записи дадут другой хеш, то есть корпус зафиксирован *вместе с содержимым* записей.
Корпус не редактируется (в API нет операции изменения).

### 6.2. Запуск

`POST /projects/{id}/runs` с `{versionId, corpusId}` → `App.StartRun`:

1. `newRun` под блокировкой проекта добавляет `VerificationRun` в статусе `running`, **заранее копируя** в него
   идентификаторы и хеши версии и корпуса, имя интерпретации, текущие `overlapPolicy`/`checksumPolicy` и
   `engine.Version`;
2. запускается задача `verification` (раздел 10), ответ `202 {run, jobId}`;
3. `executeRun` загружает сессии корпуса через `p.session` (кэш анализов) и привязанные к ним действия, вызывает
   `engine.Verify` и сообщает прогресс (0,1…0,95);
4. сессии корпуса, которые не удалось загрузить (запись не открылась или изменена), **не пропускаются молча**: в
   результат добавляется находка `capture_defect` (error), и они учитываются в `sessions` и `sessionsWithErrors`;
5. результат сохраняется одним `p.update`: находки получают идентификаторы `<runId>-f<N>`, запуск — `summary`,
   `status: succeeded`, `finishedAt`, `durationMs`, `previousRunId`.

Отмена (контекст: пользователем или остановкой программы) → статус `cancelled`; ошибка → `failed` с текстом; процесс
убит посреди проверки → при следующем запуске `failed` с текстом «Прервано: сервер был остановлен во время выполнения»
(`failInterrupted`, 10).

### 6.3. Что считает `engine.Verify`

(`internal/engine/verify.go`) Сессии обрабатываются **последовательно** в порядке корпуса. Для каждой строится «ленивый»
режим (`newBuilder(in, lean=true)`): сообщения разбираются по одному и сразу учитываются в счётчиках, не накапливаясь
(отсюда низкая память на 100 000 сообщений). Результат каждой сессии копится в собственный `tally` и **сливается в
итоговый только после успеха**: паника или ошибка одной сессии (`recover` в `verifySession`) оставляет общий итог
нетронутым, добавляет находку `capture_defect` «Ошибка обработки сессии» и увеличивает `sessionsWithErrors`.
Контекст проверяется между сессиями и каждые 4096 сообщений.

Сводка (`model.RunSummary`) охватывает **весь корпус**, а не выборку:

| Поле | Как считается |
|---|---|
| `sessions`, `sessionsWithErrors` | сессий в корпусе; сессий с пропусками/конфликтами записи или сообщениями, кроме `ok` и `unknown_type`, либо упавших в движке, либо недоступных (6.2, п. 4) |
| `messages`, `ok` | всего сообщений; со статусом `ok` |
| `violations` | сообщения со статусом `violation` (нарушения полей внутри `partial`/`ambiguous` сообщений идут в находки, но не в этот счётчик) |
| `partial`, `ambiguous`, `unknownType` | по статусам сообщения (5.8) |
| `unknownBytes` | байты вне сообщений (`Unframed`) + вся длина сообщений без правила + непокрытые полями диапазоны сообщений, разобранных по правилу, **кроме** `partial` |
| `totalBytes` | суммарная длина всех сообщений |
| `inapplicableRules` | правила, которые **не сработали ни на одном сообщении корпуса** (они не проверены) |
| `byRule` | на каждое правило: сколько сообщений подошло и сколько из них нарушений |

### 6.4. Находки и примеры происхождения

Находки группируются по ключу, чтобы тысяча одинаковых нарушений не превращалась в тысячу строк
(`findingKey`); у находки есть `occurrences` и **не более 5 примеров** (`maxExamples`), каждый — `SourceRef`.

| Вид (`kind`) | Серьёзность | Что описывает | Ключ группировки |
|---|---|---|---|
| `violation` | error | нарушение поля: `expect`, `enum`, `checksum`, утверждение | правило + путь поля (индексы массива заменены на `[]`) + вид проверки |
| `partial` | warning | сообщение неполное | правило |
| `ambiguous` | warning | подошло несколько правил | набор правил |
| `capture_defect` | warning/error | потерянные сегменты, усечения, конфликты записи, ошибка обработки сессии | причина пропуска / конфликт / сессия |
| `unknown_type` | info | не описаны ни одним правилом | направление + первые два байта |
| `unknown_region` | info | байты внутри сообщения не объяснены полями | правило + позиция (для хвостов — по размеру) |
| `unknown_region` | warning | байты вне сообщений (`Unframed`): синхронизация кадров потеряна | одна находка на весь корпус |
| `inapplicable_rule` | info | правило не сработало на корпусе — «его корректность не проверена» | правило |

Находки сортируются по важности вида (нарушения, неполные, неоднозначные, дефекты записи…), внутри вида — по убыванию
числа случаев; находки о недоступных сессиях (6.2, п. 4) дописываются в конец после сортировки.

Нарушение поля внутри массива намеренно даёт **три** находки `violation`: для массива (`entries`), для элемента
(`entries[]`) — у обоих статус `violation` распространяется вверх, текст «Нарушение правила» — и для самого поля
(`entries[].value`) с текстом проверки. Счётчик `violations` при этом считает сообщение один раз.

Пример реальной находки демо-проекта (`GET /runs/{id}/findings`):

```json
{
  "id": "run-dddfc8a2672e-f1", "runId": "run-dddfc8a2672e",
  "kind": "violation", "severity": "error",
  "ruleId": "set_param_req", "fieldPath": "value",
  "message": "88 ≠ params.value = 600 (действие «Интервал отчёта 600 с», проверка a-set-value)",
  "occurrences": 2,
  "examples": [{
    "captureId": "cap-7ecd5d4158ba",
    "captureSha256": "86297348f00c78553e38bd897bf2239dbbb5102cab6f5c83e2c6584018bd1e7e",
    "sessionId": "cap-7ecd5d4158ba-000", "direction": "c2s",
    "offset": 6, "length": 1, "packetNumbers": [4]
  }, …]
}
```

Пример — это не цитата, а *адрес*: сессия, направление, смещение и длина в потоке, пакеты, на которых он держится,
и SHA-256 записи.

### 6.5. `previousRunId` и динамика

`previousRun` выбирает **последний более ранний успешный запуск той же интерпретации на том же корпусе** (сравнение по
`startedAt` с точностью до миллисекунды, при равенстве — по порядку создания). Бэкенд хранит только ссылку; сравнение двух
сводок («что изменилось») выполняет интерфейс, запрашивая оба запуска (`RunDetailsPage`).

### 6.6. Устаревание результатов

(`project.runDTO`, вычисляется при каждом чтении запуска) `stale = true`, если запуск `succeeded` и выполнено хотя бы
одно из условий, причины перечисляются в `staleReasons`:

| Условие | Текст |
|---|---|
| у интерпретации есть версия новее `run.version` | «Проверка выполнена на vN, актуальная версия интерпретации — vM» |
| `corpus.hash` ≠ `run.corpusHash` | «Состав корпуса изменился после проверки» |
| текущие `overlapPolicy`/`checksumPolicy` проекта ≠ записанным в запуске | «Изменены настройки восстановления потоков проекта» |

Старый результат **никогда не удаляется и не пересчитывается молча**: он остаётся в `project.json` вместе с находками, а
интерфейс и отчёт показывают пометку об устаревании (`report.Markdown` добавляет «Результат устарел: …»). Смена настроек
проекта сбрасывает кэши и запускает повторный анализ записей (`UpdateProject` → `invalidate`), но существующие запуски
только получают `stale`. Следствия и границы этого механизма (корпус нельзя изменить через API; `targetPorts` и версия
движка не входят в причины устаревания) — в разделе 17.

## 7. Происхождение и целостность

### 7.1. `SourceRef`

`model.SourceRef` (`internal/model/model.go`):

```text
captureId, captureSha256   — какая запись (и её неизменяемое содержимое)
sessionId                  — "<captureId>-<индекс сессии>", индекс детерминирован порядком первых пакетов
direction                  — c2s | s2c
offset, length             — диапазон в ВОССТАНОВЛЕННОМ ПОТОКЕ направления
packetNumbers              — пакеты записи, на которых держатся эти байты
```

Ссылка в координатах **потока**, а не сообщения, правила или поля. Поток — результат сборки, а не интерпретации; он
зависит от записи и настроек восстановления, но не от кадрирования.

### 7.2. Наблюдения и `snapshotHex`

Наблюдение (`Observation`) — заметка исследователя, привязанная к диапазону байтов. `addObservation` (`internal/app/research.go`):
сверяет `captureSha256` и `captureId` источника с записью сессии (иначе `409 source_mismatch`); ограничивает диапазон 64 КиБ
и требует, чтобы он лежал в потоке (проверка без сложения `offset + length`, чтобы огромные значения не переполнили
`int`, `TestObservationRangeDoesNotOverflow`); проверяет, что все `hypothesisIds` существуют, **до** того как
связать хотя бы одну гипотезу (отклонённый запрос ничего не меняет; повторы id сохраняются один раз —
`TestRejectedCreateLeavesLinksUntouched`; так же устроено создание гипотезы с `observationIds` в `addHypothesis`);
вычисляет `snapshotHex` — шестнадцатеричный снимок байтов диапазона **в момент создания**, где неизвестные байты — `??`;
вычисляет номера пакетов по сегментам потока.

Поле `integrity` не хранится, а **пересчитывается при каждом чтении** (`ListObservations`): снимок текущих байтов
диапазона сравнивается с `snapshotHex`; не совпал или диапазон вышел за поток → `mismatch`. Поэтому смена политики
перекрытий, которая изменила байты, не привяжет наблюдение молча к другим данным: оно станет `mismatch`.

### 7.3. Целостность записи при открытии

SHA-256 файла считается при каждом анализе (`analyze`, `io.TeeReader`) — то есть при старте (`Preload`), при повторном
анализе после смены настроек и при импорте проекта. Результат сравнивается с хешем, записанным при импорте:

- `Capture.integrity` = `ok` / `mismatch` / `unchecked` (пока анализ не выполнен или запись не готова) —
  `project.captureDTO`;
- при расхождении в начало диагностики записи добавляется `integrity_mismatch` (error) «исходная запись изменена, выводы
  по ней недостоверны»;
- если файл исчез, запись получает статус `error` и диагностику с причиной.

### 7.4. Почему смена кадрирования не перепривязывает наблюдение к другим байтам

1. Наблюдение и находки ссылаются на `(сессия, направление, смещение, длина)` в потоке; интерпретация лишь группирует
   байты потока в сообщения и поля, но **не меняет сам поток и его координаты**.
2. Номер сессии — `<captureId>-<индекс по порядку первого пакета>` и не зависит от интерпретации.
3. Даже если изменилась сборка (политика перекрытий, суммы), `snapshotHex` вскроет подмену (`integrity: mismatch`), а
   гипотеза/отчёт увидят это при следующем чтении.
4. Контрпримеры гипотез — тоже `SourceRef` (+`runId`); находка проверки цитирует примеры так же (6.4), поэтому
   «пример нарушения» всегда указывает на те же байты, что и в потоке.

## 8. Хранение и перенос проекта

### 8.1. Структура каталога данных

(`internal/store/store.go`, комментарий пакета)

```text
<data>/
└── projects/
    ├── <projectId>/                         # prj-<12 hex>; один проект = одна папка
    │   ├── project.json                     # всё состояние проекта (см. ниже)
    │   ├── captures/<sha256>.pcap | .pcapng # исходные записи, имя = SHA-256, расширение по формату
    │   ├── captures/.upload-*               # временный файл приёма записи (до rename)
    │   └── reports/<reportId>/              # артефакты отчётов, пишутся один раз
    │       ├── report.<имя>.v<N>.md
    │       ├── interpretation.<имя>.v<N>.json
    │       ├── results.<имя>.v<N>.json
    │       └── examples.<имя>.v<N>.json
    ├── .upload-*.zip                        # временный файл приёма архива проекта
    └── .import-*/                           # временный каталог распаковки
```

Все пути внутри проекта **относительные** (`captures/<sha256>.pcapng`), поэтому папку можно скопировать или заархивировать и
открыть на другой машине. Каталоги, имя которых начинается с точки, `Store.List` пропускает. Временные файлы и каталоги
(`.tmp-*`, `.upload-*`, `.import-*` в `projects/`, в каталоге проекта, в `captures/` и в `reports/<id>/`) старше часа
удаляются при запуске (`Store.RemoveStaleTemp` из `app.New`): их оставляет убитый процесс, а распакованный архив может
занимать гигабайты; возраст защищает работу другого процесса, идущую прямо сейчас (`TestStaleTemporaryFilesRemovedOnStart`).

Папка проекта загружается, только если `project.id` в её `project.json` совпадает с именем папки (`Store.Load`): все
сохранения идут в `projects/<id>/`, и копия папки под другим именем (резервная копия рядом) иначе подменила бы оригинал
и перезаписала его `project.json` своим состоянием. Такая папка пропускается с ошибкой в журнале
(`TestProjectFolderCopyDoesNotShadowTheProject`).

### 8.2. Формат `project.json`

`store.State` (`SchemaVersion = 1`) — один JSON-файл с отступами, содержащий:

| Поле | Содержимое |
|---|---|
| `schemaVersion` | версия формата; если в файле значение **больше** поддерживаемого — проект не загружается (`LoadDir`), остальные проекты открываются |
| `project` | название, описание, настройки (`overlapPolicy`, `checksumPolicy`, `targetPorts`) |
| `captures[]` | метаданные записи + `file` (относительный путь) + статус, диагностика, SHA-256 |
| `actions[]` | журнал действий |
| `interpretations[]`, `versions[]` | интерпретации и их неизменяемые версии со спецификацией и хешем |
| `hypotheses[]`, `observations[]` | гипотезы (с историей статусов) и наблюдения (со снимком байтов) |
| `corpora[]` | корпуса с хешем |
| `runs[]` | запуски проверки **вместе с находками** (`RunRecord{run, findings}`) |
| `reports[]` | отчёты и перечень их артефактов (имя, размер, SHA-256) |

**Не хранится** ничего, что восстанавливается из записей: сессии, потоки, пакеты, сообщения, диагностика сборки. Они строятся
заново при первом обращении и всегда соответствуют записи и настройкам проекта.

**Проверка путей при загрузке** (`store.LoadDir` → `State.checkPaths`). `project.json` приходит и из чужих архивов, а
некоторые его значения становятся путями файловой системы. Поэтому при каждой загрузке (старт, импорт) проверяется:
id проекта (имя его каталога) и id отчётов (имена `reports/<id>/`), а также имена артефактов отчётов — простые имена
файлов (`isFileName`: непустые, не `.`/`..`, без `/`, `\` и `:`, не начинаются с точки); у каждой записи `sha256` — 64
строчных hex-символа, `format` — `pcap` или `pcapng`, а `file` — ровно `captures/<sha256>.<format>`. Нарушение — ошибка
загрузки проекта (при старте он пропускается, при импорте — `422 invalid_archive`), так что значение вроде `../x` до
файловой системы не доходит (`TestLoadRejectsPathsOutsideTheProject`, `TestImportRejectsCapturePathTraversal`).

### 8.3. Надёжность записи

- **Атомарная запись** (`store.WriteFileAtomic`): данные пишутся во временный файл в том же каталоге
  (`os.CreateTemp`, префикс `.tmp-`, права `0600`), затем `Sync`, `Close` и `os.Rename` поверх целевого. При падении
  процесса остаётся либо старый, либо новый файл целиком, не половина. Тест `TestSaveLoadRoundTrip` проверяет отсутствие
  временных файлов. Каталог после `rename` не синхронизируется (`fsync` каталога нет), а файл записи при приёме и
  файлы распакованного архива не синхронизируются перед тем, как на них сошлётся `project.json`; поэтому при внезапной
  потере питания гарантии зависят от файловой системы.
- Изменения проекта идут через `project.update` (`internal/app/project.go`): под блокировкой проекта `p.mu`
  функция меняет состояние **на месте**, и если она вернула `nil`, вызывается `save()`, который ставит
  `project.updatedAt = now` и перезаписывает **весь** `project.json` (`Store.Save` → `store.Encode` ставит `schemaVersion`). Ошибка
  функции отменяет только сохранение, не изменения в памяти, поэтому функция должна сначала проверить ввод, а потом
  менять: так сделаны `UpdateProject` (изменения собираются в копии, `TestUpdateProjectIsAtomic`) и `UpdateHypothesis`;
  создание гипотезы и наблюдения этого правила не соблюдают (раздел 17, п. 14). Окончание импорта записи
  (`indexCapture`) делает то же вручную: `p.mu` + `p.save()`. Номер задачи у записи (`jobId`) пишется в память без
  сохранения и попадает на диск со следующим сохранением.
- Исходные записи пишутся один раз (временный файл + `rename`) и больше не изменяются.
- Блокировка между процессами **отсутствует**: два экземпляра ProtoLab на одном каталоге данных не защищены друг от друга
  (в коде нет файловой блокировки).

### 8.4. Экспорт

`GET /projects/{id}/export` → `App.ExportProject` → `Store.ExportZip`:

- под блокировкой проекта `p.mu` состояние **из памяти** сериализуется в байты `project.json` (`store.Encode`), и
  блокировка сразу отпускается; эти байты пишутся в zip первыми;
- затем без блокировки обходится каталог проекта, и в zip идут остальные файлы **с относительными путями через `/`**
  (файл `project.json` с диска пропускается; файлы и каталоги с именем, начинающимся с точки, — временные — тоже).
  Это безопасно, потому что записи не меняются, а артефакты отчётов пишутся один раз; файл, исчезнувший за время
  экспорта (отменённый импорт записи), просто не попадает в архив;
- `captures/*` кладутся без сжатия (`zip.Store`: pcap плохо сжимаются, и экспорт остаётся быстрым), остальное — `Deflate`;
- имя файла в `Content-Disposition` — `<projectId>.protolab.zip`; тело стримится прямо в ответ.

Медленное или зависшее скачивание поэтому не блокирует ни проект, ни список проектов (`TestExportDoesNotBlockTheProject`).
Ошибка посреди записи (заголовки уже отправлены) только журналируется: оборванный zip обнаруживает клиент.
Архив — это содержимое папки проекта с актуальным `project.json`, а значит и **переносимый вид проекта**.

### 8.5. Импорт и проверка архива

`POST /projects/import` → `App.ImportProject` (`internal/app/projects.go`, `internal/store/archive.go`):

1. Тело копируется во временный файл `projects/.upload-*.zip` с лимитом `8 × MaxCaptureBytes` (`413 archive_too_large`).
2. `Store.ExtractZip` распаковывает во **временный каталог** `projects/.import-*`. Сначала (`acceptedEntries`), **до
   записи на диск**, проверяются все записи архива по центральному каталогу zip:
   - число файлов ≤ 10 000 (центральный каталог при этом уже прочитан `zip.NewReader` целиком);
   - имя нормализуется (`path.Clean`, `\` → `/`) и отвергается, если абсолютное, равно `..`/начинается с `../` или содержит `:`
     (защита от zip-slip, пути Windows);
   - принимаются только `project.json`, `captures/…`, `reports/…`; чужие файлы **молча пропускаются**; без `project.json` архив
     недопустим;
   - повторяющиеся имена (в том числе отличающиеся только регистром: на нечувствительной к регистру ФС это один файл) и
     файл там, где нужен каталог, отвергаются;
   - заявленный размер `project.json` ≤ 128 МиБ (`store.DefaultMaxStateBytes`: файл читается в память целиком);
   - сумма заявленных размеров ≤ бюджета `min(2 × 8 × MaxCaptureBytes, max(100 × размер архива, MaxCaptureBytes))`:
     настоящий архив распаковывается примерно в свой размер (записи лежат без сжатия), а маленькая zip-бомба не должна
     заполнить диск.

   `archive/zip` отвергает запись, которая распаковывается не в заявленный размер, поэтому заявленные размеры
   ограничивают и записанное; при распаковке бюджет дополнительно сверяется с реально прочитанными байтами (читается на
   1 байт больше остатка). Файлы создаются с `O_EXCL`; при любой ошибке временный каталог удаляется целиком; все такие
   отказы — `422 invalid_archive` (`TestExtractRejectsBadArchives`, `TestExtractRejectsClashesAndOversizedEntries`,
   `TestImportRefusesZipBombs`).
3. `store.LoadDir` читает `project.json`: JSON, `schemaVersion` не выше поддерживаемого, непустой id проекта, пути из
   `project.json` (`checkPaths`, 8.2); затем `checkImportIDs`: id проекта и **всех** сущностей должны иметь вид
   `^[A-Za-z0-9_-]{1,64}$` (как генерирует ProtoLab: они становятся именами каталогов, сегментами URL и заменяются как
   JSON-токены в `remapIDs`). Любая ошибка — `422 invalid_archive` (`TestImportRefusesForeignIDs`).
4. Дальше — `installImport` под `App.importMu`: импорты выполняются по одному от проверки идентификаторов до регистрации,
   так что два импорта одного архива (двойной щелчок, две вкладки) не займут один id (`TestConcurrentImportsOfOneArchive`).
   Если проект или любой объект с такими же идентификаторами уже загружен, **или** каталог `projects/<id>` уже существует
   (например, проект в нём не загрузился), **все идентификаторы перевыпускаются** (`remapIDs`): новые id для проекта и всех
   сущностей с прежним префиксом (если префикс длиннее 16 символов — `obj`, чтобы новый id снова проходил проверку п. 3,
   `TestRemappedIDsStayImportable`), замена по точным кавычечным токенам JSON (`"cap-…"`), включая идентификаторы сессий
   вида `cap-xxxx-003`, идентификаторы находок и каталог отчёта. Ссылки между сущностями сохраняются.
5. Состояние нормализуется, `project.json` записывается атомарно, каталог переименовывается в `projects/<id>` (одно
   атомарное действие), проект регистрируется. Как при старте, вызываются `failInterrupted` (архив мог быть сделан во
   время проверки или отчёта — они становятся `failed`) и `resumeIndexing` (во время импорта записи).
6. Запускается задача `import_project`: для каждой записи заново считается SHA-256 и восстанавливаются потоки
   (`p.analysis`), так что целостность проверена сразу (раздел 7.3); записи, не дождавшиеся индексации, индексируются
   отдельной возобновлённой задачей.

### 8.6. Воспроизводимость на другой машине

Чтобы проект воспроизвёлся, достаточно папки/архива:

- записи — те же байты (проверка по SHA-256);
- сессии, потоки и сообщения — **чистая функция** записей и настроек (`overlapPolicy`, `checksumPolicy`, `targetPorts`);
- версии интерпретаций, корпуса, гипотезы, наблюдения (со снимками) и результаты проверок лежат в `project.json`;
- `protolab verify` на другой машине без ProtoLab-проекта: достаточно записей и файла примеров; оба лежат в комплекте
  отчёта (разделы 9.3, 9.5).

## 9. Отчёты и повторное применение

### 9.1. Что такое отчёт

`POST /projects/{id}/reports` с `{title, versionId, runIds}` → `App.CreateReport` (`internal/app/reports.go`). Условия:
версия существует; каждый запуск `succeeded` и **выполнен именно на выбранной версии** (иначе файл примеров
не воспроизводил бы запуск; `422`). Создаётся запись отчёта со статусом `pending` и запускается задача `report`:
`renderReport` собирает входные данные (`reportInput`), вызывает `report.Render`, **атомарно пишет** артефакты в
`reports/<id>/` и записывает в отчёт их список (имя, размер, SHA-256) со статусом `ready`. Артефакты не изменяются
после записи: отчёт — снимок исследования. Сбой или отмена → `failed`; процесс убит посреди формирования → `failed`
при следующем запуске (`failInterrupted`; у отчёта нет поля с причиной).

### 9.2. Артефакты

| Файл | `kind` | Содержимое |
|---|---|---|
| `report.<имя>.v<N>.md` | `report_md` | читаемый отчёт: описание протокола и полей (с основанием: структура / гипотеза / подтверждено), проверки по журналу, прогоны на корпусах со сводками, находками и пометкой об устаревании, гипотезы с основаниями-наблюдениями (`snapshotHex`), контрпримерами и альтернативами, открытые вопросы, команды повторного применения |
| `interpretation.<имя>.v<N>.json` | `interpretation` | спецификация версии + служебный объект `$meta` (`name`, `version`, `hash`, `createdAt`) |
| `results.<имя>.v<N>.json` | `results` | для каждого включённого запуска: запуск (с `stale`/`staleReasons` на момент создания), корпус, находки |
| `examples.<имя>.v<N>.json` | `examples` | формат `protolab-examples/v1`: имя файла спецификации, её хеш, версия движка, настройки восстановления потоков (`overlapPolicy`, `checksumPolicy`, `targetPorts`; в файлах без `checksumPolicy` подразумевается `warn`) и по каждому корпусу — список сессий (путь записи, SHA-256, номер `tcpStream`, клиент, сервер, связанные действия), **ожидаемая сводка** и, если запуск выполнен с другими настройками, собственные `settings` корпуса (`TestExamplesRecordRunSettings`) |

Настройки в файле примеров — это настройки **запусков**, а не текущие настройки проекта: общие `overlapPolicy` и
`checksumPolicy` берутся из первого включённого запуска (`VerificationRun.settings`), корпус с иными получает свои.
`targetPorts` в запуске не записываются, поэтому в файл попадают текущие порты проекта (раздел 17).

Отчёт формируется в **Markdown** и JSON; HTML-отчёта нет. Имена файлов строятся из названия интерпретации
(`report.Slug`: латиница и цифры через дефис, при пустом результате `spec`). Скачивание — `GET /reports/{id}/files/{name}`;
имя проверяется по списку зарегистрированных артефактов отчёта (`ReportFile`), так что произвольный путь запросить нельзя, а
ответ идёт с `Content-Disposition: attachment`.

### 9.3. Комплект отчёта (`GET /reports/{id}/bundle`)

Кнопка «Комплект (.zip)» на странице отчётов скачивает `GET /reports/{id}/bundle` → `App.ReportBundle`
(`internal/app/reports.go`). Это пакет для передачи другому инженеру: в одном zip лежат четыре артефакта отчёта (в
корне) и исходные записи, на которые ссылается файл примеров, под их путями в проекте (`captures/<sha256>.pcap[ng]`).
Раскладка совпадает с папкой проекта, поэтому в распакованном каталоге без флагов работает
`protolab verify --examples examples.<имя>.v<N>.json` (`TestReportBundleReproduces`).

- Имя файла — имя Markdown-отчёта с `.zip` вместо `.md` (`report.<имя>.v<N>.zip`).
- Записи берутся только из `examples` и только если такой путь есть среди записей проекта (пути проверены при
  загрузке, 8.2); каждая кладётся один раз, без сжатия (`zip.Store`), артефакты — `Deflate`.
- Отчёт не в статусе `ready` → `409 not_ready`. Под `p.mu` берутся только отчёт и перечень записей проекта; файл
  примеров читается и архив пишется потоком в ответ уже без блокировки проекта (в отличие от экспорта, 8.4); ошибка
  посреди записи только журналируется (заголовки уже отправлены).

### 9.4. `protolab apply`

```text
protolab apply --spec F --input F [--out F|-] [--port N] [--all] [--overlap first|last] [--strict]
```

(`cmd/protolab/offline.go`: `runApply`) Применяет интерпретацию к записи **без проекта и без интерфейса**:

1. `loadSpec` читает файл (допускает `$meta` — `report.StripMeta`), `spec.Parse`; ошибки печатаются списком `путь: текст`.
2. Порт устройства: `--port`, иначе `spec.transport.port`; он становится единственным целевым портом (нет порта — целевыми
   считаются все сессии). Политика перекрытий — `--overlap` (`first` или `last`, другое значение — ошибка),
   контрольные суммы — всегда `warn`.
3. `app.AnalyzeFile` — **тот же конвейер**, что и импорт в проект (`analyzeFile`) с теми же пределами анализа
   (`DefaultLimits`: пакеты, сессии, потоки); предел размера файла `MaxCaptureBytes` проверяется только при загрузке в
   проект, к файлу на диске он не применяется.
4. Для целевых (или всех, `--all`) сессий вызываются `engine.ParseSession` (сообщения) и `engine.Verify` (сводка).
   Журнал действий в `apply` не передаётся, поэтому утверждения не проверяются.
5. Результат — JSON: `tool`, `version`, `spec` (файл, протокол, хеш), `capture` (файл, `sha256`, формат, число пакетов,
   диагностика), `summary`, `sessions[]` (номер `tcpStream`, клиент, сервер, статус, сообщения). Краткая сводка — в stderr.

| Код выхода | Когда |
|---|---|
| `0` | успех |
| `1` | ошибка (нет файла, неверная спецификация, ошибка анализа, нет обязательных `--spec`/`--input`) |
| `2` | ошибка разбора флагов |
| `3` | только с `--strict`: есть нарушения (`violations > 0`) или неполные сообщения (`partial > 0`) |

### 9.5. `protolab verify`

```text
protolab verify --examples F [--spec F] [--base DIR]
```

(`runVerify`) Читает `examples.*.json` отчёта (`format` должен быть `protolab-examples/v1`), загружает спецификацию (рядом с
файлом примеров, либо `--spec`) и **сверяет её хеш и версию движка** с записанными (расхождение — предупреждение в stderr,
но не отказ). Для каждого корпуса:

1. находит записи по относительному пути (`captureRoots`: `--base`, иначе каталог файла примеров и до четырёх каталогов
   вверх). Каталог файла примеров сначала делается абсолютным (`filepath.Abs`), поэтому относительный путь
   (`protolab verify --examples examples.x.json`, запуск из папки отчёта `reports/<id>/` или из распакованного комплекта)
   тоже находит `captures/` проекта двумя уровнями выше (`TestCaptureRootsFromRelativeExamplesPath`);
2. анализирует запись (`app.AnalyzeFile` с настройками корпуса из примеров: собственными либо общими, `exampleSettings`;
   анализ одной записи с одними настройками переиспользуется между корпусами), **проверяет SHA-256** («запись
   изменена» — проблема);
3. выбирает сессию по тройке `tcpStream` + клиент + сервер, подставляет сохранённые действия (утверждения
   работают);
4. вызывает `engine.Verify` и сравнивает сводку с ожидаемой: число сессий, сессий с ошибками, сообщений, `ok`, нарушений,
   неполных, неоднозначных, неизвестного типа, неописанных и общих байтов, неприменимые правила и по каждому правилу
   «сообщений/нарушений».

Печатает «совпадает» либо «РАСХОЖДЕНИЕ» с перечнем различий. Код выхода: `0` — все корпуса совпали, `1` — расхождение или
ошибка, `2` — ошибка флагов. Находки (`findings`) не сравниваются, сравнивается сводка.

Проверено на демо-проекте: и из `reports/<id>/` проекта, и из распакованного комплекта (9.3) команда
`protolab verify --examples examples.thermolink.v3.json` без флагов печатает «совпадает» и выходит с кодом `0`.

### 9.6. Почему результаты воспроизводимы (детерминизм)

- **Чистые функции от данных.** В `pcap`, `netpkt`, `tcpflow`, `spec` и `engine` (без тестов) нет ни `time.Now`, ни
  случайных чисел, ни горутин, ни `sync` (проверено поиском по коду): время берётся только из меток записи, обработка идёт
  последовательно, а там, где результат зависит от порядка обхода отображений, порядок зафиксирован (`keyOrder` в
  находках, сортировка кодов диагностик, `sort.SliceStable`). Глобальные переменные — неизменяемые таблицы (ошибки,
  тексты, порядок видов находок) и два крючка для тестов (`tcpflow.build`, `engine.testHookSession`).
- **Сессии упорядочены** по номеру первого пакета (`finish`), индекс сессии — часть её идентификатора.
- **Канонический хеш** спецификации и корпуса (5.2, 6.1).
- **Одна реализация.** UI-проверка, `apply` и `verify` вызывают одни и те же `AnalyzeFile`/`ParseSession`/`Verify`.
- **Проверено прямо:** два запуска `protolab apply` на одной записи дают побайтно равные JSON (SHA-256 совпадает);
  `demo.Build` детерминирован (`TestBuildIsDeterministic`); сборка `tcpflow` сверена с наивной побайтовой моделью (раздел 14).
- Идентификаторы ProtoLab (`prj-…`, `run-…`) случайны, но они лежат вне результатов `apply`/`verify`; в `examples` сессии
  заданы не ими, а путём записи, SHA-256, `tcpStream` и конечными точками.

| Аспект | Как устроено |
|---|---|
| Запуск | `Manager.Start(projectID, kind, title, fn)`: создаёт контекст `WithCancel(base)`, добавляет задачу **в начало списка**, запускает `fn` в **собственной горутине** и сразу возвращает снимок (`status: running`) |
| Очередь | **Нет**: каждая задача стартует немедленно, пула воркеров и ограничения параллелизма нет (в `model.Job.Status` перечислено и `queued`, но менеджер его не присваивает) |
| Прогресс | `Progress(fraction, stage)` — функция, которую тело вызывает по ходу дела: доля зажимается в `[0,1]`, этап — текстовая подпись; обновления сериализуются мьютексом менеджера. Импорт записи: чтение — до 0,8, сборка 0,85, индексация 0,95; проверка: 0,1…0,95 по числу сессий |
| Результат | успех → `status: succeeded`, `progress: 1`, `result: {type: capture \| run \| report \| project, id}` |
| Ошибка | возврат ошибки → `failed` + текст; **паника** тела перехватывается (`safeCall`) и превращается в ошибку «internal error: …» — одна сломанная задача не роняет сервер |
| Отмена | `POST /jobs/{id}/cancel` → `Manager.Cancel`: отменяет контекст и **ждёт до 10 с**, пока тело вернётся. Тело должно само проверять `ctx` (анализ — каждые 1024 пакета, проверка — между сессиями и каждые 4096 сообщений, импорт проекта — между записями, отчёт — один раз перед рендером). Итог: тело вернулось со статусом `cancelled` → `200` и снимок задачи; задача уже была завершена либо завершилась сама (успешно или с ошибкой), пока шла отмена → `ErrNotCancellable`, HTTP `409 not_cancellable` (в теле только код ошибки, состояние — через `GET /jobs/{id}`); тело не вернулось за 10 с → `200` с текущим снимком (`running`) (`TestCancel`, `TestCancelAfterCommit`) |
| Итоговый статус | тело вернуло `nil` → `succeeded` (даже если отмена пришла в последний момент: тело уже сохранило результат, и статус не должен ему противоречить); вернуло `context.Canceled` при отменённом контексте → `cancelled`; иная ошибка (в том числе паника) → `failed` |
| История | хранятся все активные и **последние 50** завершённых (`keep`) — `trimLocked`; список «новые сверху» |
| Остановка процесса | `Close()` отменяет базовый контекст и вызывает `Wait()` (ждёт `sync.WaitGroup`); задачи живут в памяти и **не переживают перезапуск**. После жёсткого завершения при следующем запуске (и при импорте архива) индексация записей возобновляется (`resumeIndexing`), а проверки `running`/`queued` и отчёты `pending` становятся `failed` (`failInterrupted`; у проверки `error` = «Прервано: сервер был остановлен во время выполнения», `jobId` очищается) — интерфейс не показывает их выполняющимися вечно (`TestInterruptedRunsAndReportsFailOnStart`) |
| Уведомление | `onEnd(job)` вызывается после завершения вне блокировки (журнал) |

Что опрашивает интерфейс (`frontend/src/entities/job/api/jobApi.ts`): `GET /jobs` раз в 700 мс, пока есть активные
задачи (иначе раз в 5 с), и страницы запусков (`GET /runs/{id}`) раз в секунду, пока запуск выполняется. TUI получает те же
задачи через снимок (`Source.Snapshot`, раздел 12).

## 11. HTTP-сервер и безопасность

### 11.1. Маршрутизация и обработчики

`internal/server/routes.go`. Используется `http.ServeMux` Go 1.22 с шаблонами «метод + путь + подстановки»
(`"GET /api/v1/projects/{projectId}"`, значения — `r.PathValue`). Обработчик возвращает `error`; единая обёртка
передаёт его в `server.fail`. Неизвестный путь под `/api/` — JSON `404 not_found` (а не страница SPA). Контракт
конечных точек — `docs/api.md`; бизнес-логики в обработчиках нет — они вызывают методы `app.App`.

Цепочка middleware (`server.New`): `recoverer → logRequests → guard → securityHeaders → mux`.

- `recoverer` перехватывает панику обработчика → `500` с JSON-ошибкой и стеком в журнале (`http.ErrAbortHandler` пробрасывается);
- `logRequests` пишет запросы API: мутации и ошибки — `Info`, успешные `GET` — `Debug`, 5xx — `Error`.

### 11.2. Соглашения JSON и ошибок

- JSON в `camelCase`; время — RFC 3339 в UTC: метки пакетов и сообщений — с 9 знаками долей секунды
  (`model.PacketTime`), времена объектов (`createdAt` и др.) — с миллисекундами (`model.Now`); списки —
  `{"items": […], "total": N}` (`model.List`: `null` не бывает); долгие операции — `202 Accepted` + `jobId`.
- Ошибка — конверт `{"error": {"code": "snake_case", "message": "…", "details": …}}`. Сервисный слой возвращает `*app.Error`
  со статусом, стабильным кодом, сообщением для человека и деталями; `server.fail` отдаёт его как есть. Остальное:
  `jobs.ErrNotFound` → `404`, `jobs.ErrNotCancellable` → `409`, превышение лимита тела → `413 too_large`, всё прочее →
  `500 internal` (с записью в журнал).
- Тело JSON-запроса (`decode`) должно быть объявлено как JSON — `Content-Type: application/json` или `*+json`, иначе
  `415 unsupported_media_type`: HTML-форма умеет отправлять только `application/x-www-form-urlencoded`,
  `multipart/form-data` и `text/plain`, поэтому межсайтовая отправка формы отклоняется даже браузером, который не шлёт
  ни `Origin`, ни `Sec-Fetch-Site` (`TestJSONBodyRequiresJSONContentType`). Размер — не больше 8 МиБ (`maxJSONBody`,
  `http.MaxBytesReader`).

### 11.3. Загрузка и выгрузка файлов

- **Загрузка** записи/архива/журнала действий — `multipart/form-data`, поле `file`; чтение потоком
  (`uploadedFile` → `MultipartReader`) без буферизации; пределы: запись — `MaxCaptureBytes + 1 МиБ`, архив проекта —
  `8 × MaxCaptureBytes + 1 МиБ`, журнал действий — 17 МиБ; внутри `app` содержимое файла ограничено точнее
  (`io.LimitReader` с запасом в 1 байт, чтобы превышение было ошибкой `413`, а не обрезкой: 4.1, 5.10, 8.5).
- **Выгрузка**: `Content-Disposition: attachment; filename=…` (`attachment` через `mime.FormatMediaType`); байты потока —
  `application/octet-stream` с заголовком `X-Stream-Length`; экспорт — zip, стримится; файлы отчётов — только зарегистрированные.

### 11.4. Встроенный SPA

`internal/webui/webui.go`: `//go:embed all:dist`; `internal/server/static.go` отдаёт как SPA: существующий файл — как есть
(`/assets/*` с `Cache-Control: public, max-age=31536000, immutable`, прочие не хешированные файлы — `no-cache`);
`index.html` — `no-cache`; **любой другой путь вне `/api/` — `index.html`** (клиентская маршрутизация); отсутствующий
`/assets/*` — `404`, а не HTML; каталоги не листаются; методы кроме `GET`/`HEAD` — `405`. Если бинарь собран без фронтенда
(`index.html` отсутствует), вместо интерфейса показывается страница-подсказка, а API работает; в журнале предупреждение
(`webui.Built`). В репозитории лежит заглушка `internal/webui/dist/README.md`, чтобы `go build` работал без сборки фронтенда.

### 11.5. Модель безопасности локального инструмента

Сервер — **однопользовательский локальный инструмент без аутентификации**; защищается он от того, что способен сделать
**веб-страница в браузере пользователя**, и от случайного выхода в сеть.

| Мера | Реализация | От чего защищает |
|---|---|---|
| привязка к `127.0.0.1` | `defaultAddr = "127.0.0.1:7420"`; запасной порт тоже `127.0.0.1:0` | недоступен из сети по умолчанию |
| проверка `Host` | `server.guard`: `Host` должен быть `localhost` или loopback-IP (`127.0.0.0/8`, `[::1]`; с портом или без), иначе `403 forbidden_host`; для **всех** методов | **DNS rebinding**: страница `evil.example`, чьё имя резолвится в 127.0.0.1, шлёт `Host: evil.example` — запрос отклонён |
| проверка `Sec-Fetch-Site` / `Origin` | для `POST/PATCH/DELETE` и др., кроме `GET/HEAD/OPTIONS`: `Sec-Fetch-Site: cross-site` **или `same-site`** → `403 cross_site`; присутствующий `Origin` должен быть loopback-адресом (в режиме `AllowAnyHost` — совпадать с `Host`) | **CSRF**: чужая страница не может отправлять изменяющие запросы. `same-site` — это страница на другом порту того же хоста (другое локальное веб-приложение): её `Origin` loopback и прошёл бы проверку, поэтому она отсекается по `Sec-Fetch-Site`; интерфейс и прокси Vite шлют `same-origin` (`TestGuardRejectsSameSitePages`) |
| JSON только с JSON-типом | `decode`: `Content-Type` не JSON → `415 unsupported_media_type` (11.2) | межсайтовая отправка HTML-формы, в том числе из браузера без `Sec-Fetch-Site`/`Origin` |
| нет CORS | заголовки `Access-Control-*` не выставляются нигде | чужая страница не может читать ответы API; предзапрос CORS для JSON-POST не получает разрешения |
| CSP и заголовки | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` | XSS, встраивание во фрейм, внешние ресурсы. CI дополнительно проверяет, что собранный UI не ссылается на внешние ресурсы (`.github/workflows/ci.yml`, job `frontend`) |
| пределы размера | JSON 8 МиБ; загрузки по лимитам выше; запись `MaxCaptureBytes` | исчерпание памяти/диска |
| безопасные имена | имя отчёта проверяется по списку; `cleanFileName` для имён записей; пути из `project.json` (`checkPaths`) и id импортируемого архива (`checkImportIDs`); zip-slip и коллизии имён в импорте (8.2, 8.5) | чтение/запись вне каталога |
| санитизация вывода | TUI очищает недоверенный текст (имена файлов, сообщения журнала) от управляющих и bidi-символов (`tui.clean`) | подмена интерфейса через вредоносное имя файла |

Если пользователь **явно** задал не-loopback адрес (`--addr 0.0.0.0:7420`), проверка `Host`/`Origin` отключается
(`Options.AllowAnyHost`), в журнал пишется предупреждение; если у изменяющего запроса есть `Origin`, он должен совпадать с
`Host`, а `Sec-Fetch-Site: cross-site`/`same-site` и не-JSON тело отклоняются по-прежнему. Это осознанный режим: сервер
тогда открыт сети без аутентификации.

Что **не** защищено (честно): любой локальный процесс или пользователь той же машины может обратиться к порту — это
локальный, не многопользовательский инструмент. В loopback-режиме допускается `Origin` любого loopback-адреса (так
работает dev-сервер Vite на другом порту): страница другого локального порта в старом браузере, который не шлёт
`Sec-Fetch-Site`, пройдёт проверку `Origin`. JSON-эндпоинты от неё защищает требование JSON-типа (JSON-запрос из
чужого источника требует предзапроса CORS, а разрешения нет), но запросы без тела (`POST /demo`,
`POST /jobs/{id}/cancel`) и загрузки `multipart/form-data` (запись, архив, журнал) ей доступны; читать ответы она не
может.

## 12. Терминальный интерфейс

### 12.1. Модель Bubble Tea

`internal/tui/tui.go`. Используется Bubble Tea v2 (`charm.land/bubbletea/v2`). Модель `ui` — обычный Elm-цикл:
`Init` → `Update(msg)` → `View`. Сообщения: `tea.WindowSizeMsg`, `tea.KeyPressMsg`, `tea.BackgroundColorMsg` (тема
терминала), `snapMsg` (новый снимок), `openedMsg`, `demoDoneMsg`, `toastEndMsg`.

`Run(ctx, opt)` сначала проверяет терминал (`isTTY`: stdin и stdout — терминал, `TERM != "dumb"`); иначе возвращает
`ErrNotTerminal` **не трогая терминал**. Запуск: `tea.NewProgram(newUI(opt), tea.WithContext(ctx), tea.WithoutSignalHandler())`;
`View` включает альтернативный экран, заголовок окна и (если идут задачи) индикатор прогресса в панели задач терминала.

### 12.2. Откуда берётся состояние: опрос снимка

TUI не знает про `app`: ему передан `Source` с единственным методом `Snapshot() tui.Snapshot`. Реализация —
`snapshotSource` в `cmd/protolab/serve.go`: версия, URL, каталог данных, `Summaries()` проектов, `Jobs().List(8)`, строки
кольца журнала, занятая куча (`heapBytes` читает `runtime/metrics`, **без** остановки мира, в отличие от
`runtime.ReadMemStats`, так как опрос идёт несколько раз в секунду), время старта.

Опрос — это `tea.Tick`, замыкание которого выполняется в горутине команды, а не в `Update`: взятие блокировок не
останавливает отрисовку. Интервал: **250 мс, пока есть задачи в работе, иначе 1 с** (`pollEvery`).

### 12.3. Горячие клавиши

| Клавиша | Действие |
|---|---|
| `o` / `Enter` | открыть веб-интерфейс в браузере (`browser.Open`) |
| `c` / `y` | скопировать адрес в буфер обмена по OSC 52 (работает и по SSH) |
| `d` | создать демо-проект (если действие передано) |
| `l` / `Tab` | журнал во весь экран; в нём `↑↓/jk`, `PgUp/PgDn`, `g/G`, `Esc` |
| `?` / `F1` | справка |
| `q` / `Ctrl+C` | выход; если идут задачи — сначала подтверждение (`y`/`Enter`/второй `Ctrl+C`) |

Клавиши журнала **не пробрасываются** в `viewport.Update`: у него свои клавиши (`l`, `d`, `f`, `b`…), конфликтующие с
горячими клавишами интерфейса. Раскладка адаптивна (узкая/широкая/«крошечная»), `clamp` гарантирует, что кадр никогда не
выше и не шире терминала (`TestViewFitsTerminal` перебирает размеры и режимы).

### 12.4. Открытие браузера

(`internal/browser/browser.go`) Нажатие `o` вызывает `browser.Open(url)` в команде Bubble Tea (отдельная горутина).

1. **Проверка адреса**: схема `http`/`https`, непустой хост, никаких пробелов и метасимволов оболочки — защита от
   инъекции в командную строку.
2. **Кандидаты** (`candidates`) в порядке приоритета: macOS — `open`; Windows — `rundll32 url.dll,FileProtocolHandler`,
   затем `powershell Start-Process`; Linux — программы из `$BROWSER` (список через `:`, `%s` — место адреса; не при WSL),
   **WSL** (по `WSL_DISTRO_NAME`/`WSL_INTEROP` или «microsoft» в `/proc/sys/kernel/osrelease`) — `wslview`,
   `rundll32.exe`, `explorer.exe` (код выхода 1 считается успехом), `powershell.exe`; при наличии `DISPLAY` или
   `WAYLAND_DISPLAY` — `xdg-open`, `gio open`, `x-www-browser`.
3. **Запуск**: `exec.LookPath`; стандартные потоки процесса — `/dev/null` (текстовый «браузер» вроде `lynx` не сможет
   рисовать поверх TUI, а болтовня `xdg-open` не попадёт на экран); на Unix — новая сессия (`Setsid`), чтобы браузер
   пережил `Ctrl+C` и закрытие терминала; на Windows — без окна консоли. Процесс всегда «дожидается» в отдельной
   горутине (нет зомби). Если за 1,5 с процесс всё ещё работает — это успех (браузер присоединился).
4. **Нет графической сессии** (SSH, контейнер: нет кандидатов) → `ErrNoDisplay`; нет программы → ошибка. TUI в этом случае
   показывает плашку «Браузер не открылся (…). Адрес скопирован в буфер.» и копирует адрес по OSC 52.

### 12.5. Журнал в памяти

`internal/logx`: `Ring` — кольцевой буфер последних **500** строк (в `runServe`); `Handler` — `slog.Handler`, форматирующий
запись как «сообщение ключ=значение …» (атрибуты и группы квалифицируются) и кладущий её в кольцо; при необходимости копирует
строки в `io.Writer` (зеркало). В режиме TUI зеркала нет (его экран занят); без терминала зеркалом служит stderr;
`SetMirror` переключает зеркало на лету (например, когда TUI закончил работу), и это распространяется на все производные
обработчики. `slog.SetDefault` перенаправляет туда же стандартный пакет `log`.

### 12.6. Без терминала

Если stdout/stdin не терминал или `TERM=dumb` — TUI не запускается вовсе (раздел 2.4), адрес печатается в stderr, журнал идёт
в stderr, остановка по `SIGINT`/`SIGTERM`. Это режим для CI, systemd, Docker; `--no-tui` включает его принудительно.

## 13. Конкурентность и память

### 13.1. Блокировки

| Объект | Тип | Что защищает | Заметки |
|---|---|---|---|
| `App.mu` | `RWMutex` | реестр: `projects`, `owner` (id сущности → id проекта) | держится кратко; чтение — `RLock` |
| `project.mu` | `Mutex` | `st` (состояние проекта), `slots` (кэш анализов), `rev` | изменения — через `project.update` (8.3); **долгая работа идёт вне `mu`** на неизменяемых снимках: анализ записи, движок (разбор, проверка, рендер отчёта), снимки наблюдений, приём файла записи, запись комплекта отчёта и архива экспорта. Под `mu` остаются сохранение `project.json` (сериализация + `fsync`) и сериализация `project.json` для экспорта (8.4) |
| `App.importMu` | `Mutex` | шаг установки импортируемого архива (`installImport`): проверка коллизий id, `rename`, регистрация | импорты одного архива не займут один id (8.5) |
| `analysisSlot` | `atomic.Bool` + канал `done` | вычисление анализа записи ровно один раз на поколение настроек | первый вызывающий выполняет `compute` (CAS), остальные ждут `done`; канал закрывается через `defer`, даже при панике |
| `messageCache.mu` | `Mutex` | LRU разобранных сессий | отдельный от `project.mu` |
| `jobs.Manager.mu` | `Mutex` | список задач и их состояние | колбэк `onEnd` вызывается **вне** блокировки |
| `logx.Ring.mu`, `mirrorWriter.mu` | `Mutex` | кольцо и запись зеркала | |
| `diskUsage.mu` | `Mutex` | кэш размера каталога данных (пересчёт не чаще раза в 30 с) | |
| `analysisSeq` | `atomic.Uint64` | сквозной номер результата анализа | входит в ключ кэша сообщений |

Результат анализа (`captureAnalysis`, `sessionData`) после построения **не изменяется**, поэтому на него без блокировок
ссылаются HTTP-обработчики, задачи и кэш. Смена настроек проекта не правит его, а создаёт новое поколение (`invalidate`
подменяет `slots`, увеличивает `rev` и очищает кэш).

### 13.2. Кэши и бюджеты памяти

| Кэш | Ключ | Бюджет | Что при переполнении |
|---|---|---|---|

### 13.3. Race detector

Весь Go-набор тестов запускается с детектором гонок: `make test-go` (`CGO_ENABLED=1 go test -race -count=1 ./cmd/... ./internal/...`)
и тем же в CI (`.github/workflows/ci.yml`, job `go`, `go test -race -count=1 -timeout 10m`). Детектору нужен cgo, поэтому
для тестов он включён, а релизные бинари собираются с `CGO_ENABLED=0`. Параллелизм в тестах возникает там, где
он есть в коде (фоновые задачи, `WaitJob`, возобновление индексации); отдельного нагрузочного теста с конкурентными
HTTP-запросами нет (раздел 17).

## 15. Сборка и релизы

### 15.1. Встраивание веб-интерфейса

1. `make web` (`Makefile`): `npm ci` (если изменился `package-lock.json`) и `npm run build` (`tsc -b && vite build`) в
   `frontend/`; сборка пишется в `internal/webui/dist`.
2. `internal/webui/webui.go`: `//go:embed all:dist` — каталог входит в бинарь целиком (`all:` берёт и файлы с точкой/подчёркиванием).
   В git лежит только заглушка `internal/webui/dist/README.md`, поэтому `go build`/`go vet`/`go test` работают и без
   сборки фронтенда; такой бинарь показывает страницу-подсказку.
3. `make verify-embed` падает, если в списке встроенных файлов (`go list -f '{{join .EmbedFiles "\n"}}' ./internal/webui`)
   нет `dist/index.html`: защита от выпуска бинаря с заглушкой. `make build` вызывает её автоматически.
4. CI дополнительно проверяет, что собранный интерфейс не ссылается на внешние ресурсы (в HTML/CSS `src`/`href`/`url()`,
   в JS `fetch`/`import` по `http(s)://`): интерфейс должен работать офлайн.

### 15.2. Кросс-компиляция

```bash
CGO_ENABLED=0 go build -trimpath -ldflags '-s -w -X main.version=$VERSION -X main.commit=$COMMIT -X main.date=$DATE' -o bin/protolab ./cmd/protolab
```

`CGO_ENABLED=0` — статический бинарь без C-библиотек и возможность собирать любую цель с одной машины
(`GOOS`/`GOARCH`); `-trimpath` убирает локальные пути (воспроизводимость), `-s -w` — таблицы символов и отладочные данные.
Шесть целей (`TARGETS` в Makefile): `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, `windows/amd64`,
`windows/arm64`. Платформенный код изолирован build-тегами (`internal/browser/detach_unix.go` / `detach_windows.go`), а CI
собирает и проверяет `go vet` под все шесть целей отдельно (job `cross`).

### 15.3. От слияния до релиза

```text
push в main ──► release.yml
   ├─ verify  = ci.yml (workflow_call): frontend · go · smoke · cross · ok
   ├─ release (только если verify зелёный)
   │    1. версия: MAJOR.MINOR из файла VERSION + "." + номер запуска  → 0.1.<N>, тег v0.1.<N>
   │    2. make web                   — интерфейс собирается один раз
   │    3. make release-local         — 6 бинарей, README.md + THIRD_PARTY_NOTICES.md в каждый архив,
   │                                     tar.gz (Windows — zip), SHA256SUMS
   │    4. make verify-dist           — scripts/verify-dist.sh (ниже)
   │    5. gh release create          — тег на коммите слияния, 6 архивов + SHA256SUMS, заметки генерирует GitHub
   └─ ручной запуск (workflow_dispatch): шаги 1–4, архивы прикладываются к запуску на 7 дней, релиз не создаётся
```

Свойства процесса (`release.yml`): релизы по push идут строго по одному (`concurrency`-группа `release`,
`cancel-in-progress: false`; ручные запуски — каждый в своей группе и ничего не публикуют);
повторный запуск того же прогона не создаёт второй релиз (если тег уже указывает на тот же коммит и релиз существует,
публикация пропускается); если тег существует на другом коммите — ошибка; если уже есть более новый релиз — публикация
завершается ошибкой и ничего не выпускает (старая сборка не станет «Latest»); право `contents: write` запрашивает только
задача публикации, остальным хватает `contents: read`.
`verify-dist.sh` проверяет: ровно шесть архивов и их `SHA256SUMS`; в каждом архиве бинарь, README и заметки; у каждого
бинаря собственные `GOOS`/`GOARCH`, `CGO_ENABLED=0`, `-trimpath=true` (из `go version -m`); каждый Go-модуль бинаря имеет
лицензию в заметках; при шрифтах в интерфейсе — текст SIL OFL; а бинарь для текущей платформы **запускается**, сообщает версию
релиза и отдаёт встроенный интерфейс.

### 15.4. Лицензии (`THIRD_PARTY_NOTICES.md`)

Файл не хранится в репозитории, а создаётся `scripts/notices.sh` при сборке: объединение `go list -deps` для **каждой** из
шести платформ (список модулей различается: например, `x/termios` не линкуется в Windows-сборку), лицензия Go (`GOROOT`),
production-зависимости `frontend/` (React, TanStack, шрифты IBM Plex под SIL OFL…) и Tailwind как инструмент, чей код
попадает в сборку. Скрипт **падает**, а не выпускает неполный файл, если у модуля или пакета нет текста лицензии.

## 16. Вопросы экспертов и ответы

**1. Почему собственный разбор PCAP, а не libpcap/gopacket?**
Исходное требование — один бинарь без зависимостей на шесть платформ с `CGO_ENABLED=0`; libpcap и cgo-обёртки этого не
позволяют. Форматы просты, а нужные нам свойства трудно получить «снаружи»: точное целочисленное время с `if_tsresol`/
`if_tsoffset` (`tsunit.go`), несколько интерфейсов и секций PCAPNG, различие «пропустить непригодный пакет»
(`PacketError`) и «файл кончился» (`ErrTruncatedFile`/`ErrCorrupt`), отказ от выделения гигабайтов по повреждённому полю
длины (`readAnnounced`). Сборка TCP тоже своя: ей нужны модель `Gap` с причиной, `Conflict` с обоими пакетами, происхождение
каждого байта по пакетам и экземпляры соединения — это основа `SourceRef`. Всё покрыто фаззингом и сверкой с наивной
моделью (раздел 14).

**2. Как отличить ретрансмиссию от конфликта?**
Только по содержимому на одних и тех же номерах последовательности. Совпали байты — дубликат: пометка `retransmission`,
смещение пакета `-1`. Отличаются — `overlap_conflict`: в `Conflict` записываются **оба** пакета, а в потоке остаются байты
по политике проекта (`first` — ранее захваченного, `last` — последнего). Ничего не теряется: расхождение видно в
`Conflicts`, в пометках пакетов и в диагностике уровня error (4.7).

**3. Что именно происходит при checksum offloading?**
Неверная сумма само по себе не отбрасывает пакет: он получает `checksum_warning`. Решает статистика по направлению: если
неверных у отправителя не меньше, чем верных, — это offloading на узле захвата (сеть ещё не досчитала сумму); данные
используются как есть, диагностика `checksum_offload` (info) со счётчиком. Если неверны единицы среди верных —
повреждение: пакет не расширяет поток, при расхождении проигрывает пакету с верной суммой независимо от политики
перекрытий, диагностика `checksum_error` (warning); без верной копии сессия остаётся `partial`. Политика `ignore` отключает
проверку (4.9).

**4. Как определяется повторное использование порта?**
Новый экземпляр соединения открывают: SYN после закрытия (FIN с обеих сторон/RST) предыдущего, SYN с другим номером,
SYN-ACK, не соответствующий SYN этого экземпляра (в том числе если SYN нового соединения не захвачен и старое «открыто»).
Запоздавшие сегменты старого экземпляра возвращаются в него по близости номеров последовательности (зазор `2²⁴`), чтобы не
превратиться в «гигабайты потерянных байтов» нового (4.6; тесты `TestPortReuse*`, `TestLateSegmentOfReplacedInstance`).

**5. Зачем относительные sequence numbers?**
Смещение в потоке — это 64-битная разность между номером и номером первого байта; она не зависит от случайного ISN и
не «заворачивается» (`seqUnwrapper`). Поэтому `SourceRef` переносимы между машинами, а числа можно сверить с Wireshark
(`tcp.relative_seq`): SYN = 0, первый байт = 1 (4.7).

**6. Что, если SYN не захвачен?**
Роль клиента выводится из SYN-ACK (тогда известны оба начала: `ack` SYN-ACK = ISN клиента + 1), из целевого порта проекта
или, в худшем случае, из первого отправителя (`Roles: inferred`/`unknown`). Без SYN-ACK начало потока оценивается как первый
увиденный байт, `startKnown = false`, диагностика `missing_handshake`, сессия никогда не `complete`. Движок знает про
неизвестное начало: `length_prefixed` ищет `sync` вместо чтения длины с нулевого смещения, у `delimiter` первое сообщение
`partial` (4.6, 4.7, 5.4).

**7. Как гарантируется, что неизвестные байты не превращаются в нули в результатах?**
Байты пропуска физически нулевые только в транспортном массиве; решения движка принимаются по маске пропусков: кадрирование
не ищет `sync`/разделитель на них и не читает на них длину; правила не совпадают на них; поля, задевающие их, получают
`unknown`/`??`/`null`; контрольные суммы по ним не проверяются; кадр из одних пропусков не создаётся; в снимке
наблюдения они `??` (5.7). Инварианты закреплены тестами (`TestFieldsOverGapBytes`, `TestFramingAccountsForEveryKnownByte`,
`FuzzParseSession`). Известный нюанс: поле, зависящее от длины, лежащей в пропуске, становится пустым, а его байты остаются
в `Unknown`.

**8. Как происхождение переживает смену кадрирования?**
`SourceRef` адресует байты потока (сессия, направление, смещение, длина), а не сообщения или поля. Смена интерпретации
меняет группировку, но не поток. Если изменились сами настройки сборки, `snapshotHex` наблюдения перестаёт совпадать
и `integrity` становится `mismatch` (7.4).

**9. Зачем хешировать версии интерпретаций?**
Результат проверки осмыслен только вместе с точной спецификацией. SHA-256 канонического JSON не зависит от форматирования, его
несут запуск проверки, отчёт и файл примеров; `verify` сверяет хеш при повторном применении. Новая версия с тем же хешем
отвергается (`no_changes`) (5.2).

**10. Как находятся устаревшие результаты?**
`runDTO` при каждом чтении сравнивает запуск с текущим состоянием: есть ли версия новее, совпадает ли хеш корпуса, те ли
настройки восстановления потоков. Старый результат не удаляется и не пересчитывается; он остаётся с `stale` и списком причин
(6.6).

**11. Как обеспечен детерминизм?**
Ядро (`pcap`, `netpkt`, `tcpflow`, `spec`, `engine`) не использует часы, случайные числа, горутины и блокировки; порядок
обходов зафиксирован; сессии упорядочены по первому пакету; хеши канонические; интерфейс, `apply` и `verify` идут через одни и
те же функции. Проверено: два запуска `apply` дают одинаковый SHA-256 результата (9.6).

**12. Какие защитные пределы и что при превышении?**
Размер записи 512 МиБ → `413`, ничего не сохраняется; пакетов 2 000 000 → `packet_limit`; сессий 20 000 → `session_limit`;
поток 64 МиБ и 1 ГиБ на запись → поток обрезается, `stream_too_large`, статус `error`; сообщений на запрос 200 000 →
`422 message_limit` (проверяется при кадрировании, до разбора, 5.4); журнал действий 16 МиБ → `413 action_log_too_large`;
архив проекта 8× размера записи (`413 archive_too_large`), распакованный объём и `project.json` — по заявленным размерам до
записи (`422 invalid_archive`). Превышение всегда видно как ошибка или диагностика, а не как молчаливое усечение (4.10,
8.5, `docs/performance.md`).

**13. Чем безопасен сервер на localhost?**
Привязка к `127.0.0.1`; проверка `Host` против DNS rebinding; `Sec-Fetch-Site` (`cross-site` и `same-site` — страница на
другом порту того же хоста) и `Origin` против CSRF; JSON-тела только с JSON-типом (`415`), так что HTML-форма их не
отправит; нет CORS; CSP без внешних ресурсов; ограничения размеров; безопасные имена файлов и защита от zip-slip. Нет аутентификации: сервер рассчитан на одного
пользователя машины (11.5).

**14. Как работает отмена?**
Контекст на каждую задачу (`WithCancel` от корневого контекста приложения). `POST /jobs/{id}/cancel` отменяет его и ждёт до
10 с возврата тела задачи; тело проверяет `ctx` в циклах (пакеты, сессии, сообщения). Результат: `cancelled` (`200`);
если тело успело закончить работу (её результат уже сохранён — статус `succeeded`) или упало (`failed`) — ответ
`409 not_cancellable`, статус задачи не подменяется на `cancelled`; если тело не вернулось за 10 с — `200` с состоянием
`running`. Остановка программы отменяет те же контексты; после жёсткого завершения недоделанный импорт записи
возобновится при запуске, а проверки и отчёты станут `failed` (раздел 10).

**15. Что не поддерживается и почему это приемлемо?**
Основной путь — IPv4 поверх Ethernet/VLAN/SLL/raw/loopback и TCP. Не собираются фрагменты IPv4; IPv6, UDP, ARP, нестандартные
типы канала пропускаются **с явной диагностикой** (код, число и номера первых пакетов), а не молча; не разбираются опции TCP/IP;
одновременное открытие соединения (simultaneous open) разбивается на две сессии. Для задачи — исследование обмена с
устройством по TCP — решающие дефекты захвата (потери, перестановки, ретрансмиссии, усечение, повторное использование порта,
offloading, начало без SYN) обработаны, а всё необработанное названо в диагностике записи. Полный список — раздел 17.

**16. Как обрабатывается переход через 2³²?**
Номера переводятся в 64-битные смещения как ближайшие к уже принятому максимуму знаковой 32-битной разностью (арифметика RFC 9293):
`high + int64(int32(seq − origin − uint32(high)))`. Тесты: `TestSequenceWraparound`, каждый пятый прогон property-теста начинается
у границы 2³².

**17. Как укладываетесь в память на 100 МиБ?**
Payload копируется в общие чанки по 1 МиБ, кадры освобождаются; при проверке сообщения разбираются по одному в «ленивом»
режиме; кэш разобранных сообщений ограничен 256 МиБ на проект по оценке байтов. Контрольная нагрузка: пик процесса ≈1,05 ГиБ,
импорт 0,76 с, разбор 100 тыс. сообщений 2,1 с (13.2).

**18. Что делает пакет, усечённый snaplen?**
Он вносит захваченные байты, помечается `truncated`, сумма — `ChecksumUnknown`; хвост (разница IP-длины и захваченного)
запоминается: если позже придёт полная копия, он будет заполнен, иначе станет `Gap{reason: truncated}` с диагностикой
`tcp_truncated`, а сессия — `partial` (`TestTruncatedPayload`).

**19. Почему перестановка пакетов не даёт пропуск?**
Сборка идёт по номерам, а не по порядку в записи. Опоздавший сегмент заполняет «дыру» и получает `out_of_order`. Пропуск —
только то, что так и не пришло к концу записи (`TestOutOfOrderAcrossGapLaterFilled`).

**20. Как избегается поток в гигабайты из-за мусорного номера?**
Размер потока вычисляется по номерам, поэтому: пакеты с неверной суммой (при большинстве верных) не расширяют поток;
запоздавшие сегменты старого экземпляра не попадают в новый; keep-alive-пробы не размещаются; и есть жёсткие пределы на
поток и на запись (4.10).

**21. Почему политика перекрытий — настройка?**
Какие из двух различающихся копий дошли до приложения получателя, по записи неизвестно (реализации стеков TCP решают
это по-разному), поэтому выбор вынесен в настройку проекта, а расхождение всегда показывается. Смена настройки
пересобирает потоки и помечает результаты проверок устаревшими; наблюдения, чьи байты изменились, получают `mismatch`.

**22. Откуда уверенность в движке?**
Сверка с независимой реализацией на TypeScript на демо-корпусе (`reference.json.gz`), фаззинг разбора, свойства и
сверка с наивной моделью для сборки, тесты каждого поведения из `docs/interpretation-format.md`. Отличия от эталона
перечислены (5.12).

**23. Может ли ProtoLab «подтвердить» назначение поля?**
Нет. `confirmed` выставляет исследователь; движок лишь показывает, согласуется ли поток с описанием, и ищет контрпримеры. Даже
проверенная сумма `sum8` в демо остаётся гипотезой, а отчёт прямо говорит, что совпадение на примерах не доказывает
назначение (5.9).

**24. Как защищён импорт чужого архива?**
Распаковка во временный каталог; нормализация и запрет абсолютных путей, `..` и `:`; только `project.json`/`captures/`/`reports/`;
до записи на диск — отказ от повторяющихся (с точностью до регистра) и конфликтующих имён, лимиты числа файлов, размера
`project.json` и суммарного объёма по заявленным размерам (бюджет зависит от размера архива: zip-бомба отсекается сразу);
при распаковке объём сверяется и по реально прочитанным байтам; `O_EXCL`; проверка схемы, путей из `project.json` и вида
всех идентификаторов; установка импортов по одному; при коллизии — перевыпуск идентификаторов; повторный анализ с
SHA-256 после импорта (8.5). Что не проверяется — в разделе 17.

**25. Что будет при падении процесса посреди работы?**
`project.json` пишется атомарно (временный файл + `rename`): остаётся либо старая, либо новая версия. Запись, импорт которой не
закончился, возвращается в индексацию при запуске. Проверки `running` и отчёты `pending`, оставшиеся после жёсткого
завершения (kill -9, потеря питания), при следующем запуске становятся `failed` с причиной «Прервано: сервер был остановлен
во время выполнения» (`failInterrupted`); их нужно запустить заново — повторного выполнения нет (раздел 10).

## 17. Известные ограничения

Список составлен по коду и экспериментам; «ограничение» здесь — осознанное решение либо место, где поведение отличается от того,
чего можно ожидать.

**Сеть и сборка потоков**

1. IPv6 не разбирается (диагностика `ipv6_unsupported`); фрагменты IPv4 не собираются (`ip_fragment`); типы канала вне списка
   (например, 802.11) — `unsupported_linktype`; сжатые файлы не читаются.
2. Контрольная сумма заголовка IPv4 не проверяется; опции TCP и IP пропускаются по длине заголовка, но не интерпретируются
   (SACK, масштаб окна, метки времени, `URG`-указатель не используются); окна и перегрузка не моделируются.
3. Одновременное открытие соединения (simultaneous open) порождает две сессии (проверено экспериментом): SYN без ACK от
   второй стороны считается новым экземпляром (`acceptsSyn`).
4. Ключ соединения не содержит интерфейса захвата; запись, в которой один пакет виден дважды (например, с двух интерфейсов), даёт
   корректный поток, но дубликаты помечены как `retransmission` (проверено экспериментом).
5. Причины пропуска — только `lost` и `truncated`; незахваченное начало потока — не пропуск, а `startKnown = false`, поэтому
   объём потерянного начала неизвестен и нигде не показывается. Запоздавший пакет старого соединения, чьи номера близки к
   номерам нового экземпляра (ISN по RFC 6528), остаётся в новой сессии (4.6): он виден в её списке пакетов, а не
   возвращается в старую.
6. Роль клиента/сервера без рукопожатия — эвристика (SYN-ACK, целевой порт, первый отправитель); она маркируется `roles`, но может
   ошибаться. Различение offloading и порчи — статистика «верных больше, чем неверных» по направлению; пакеты с усечённым
   телом в статистику не входят.
7. Байты пропусков в `Stream.Data` и `Message.data` — нули (транспорт); неизвестность несёт список пропусков.
8. Все анализы записей проекта держатся в памяти без вытеснения (для контрольной записи 97,6 МиБ — около 200 МиБ живой кучи); выгрузки из памяти нет.

**Интерпретации и проверка**

9. Типы полей: `u8 i8 u16 i16 u32 i32 bytes ascii array`; нет 64-битных чисел, вещественных, битовых полей, условных и
   вложенных структур, кроме массивов; контрольные суммы только `sum8` и `xor8`; для `length_prefixed` нужен `sync` для
   восстановления после пропуска.
10. Поле, зависящее от длины/счётчика, лежащего в пропуске, становится пустым (`length 0`, `ok`), а его байты остаются в `Unknown`;
    контрольная сумма, не проверенная из-за пропуска, остаётся `ok`.
11. Утверждения по журналу применяются к верхнеуровневым полям, берётся первое привязанное действие нужного вида; привязка
    действий к сессиям — по времени начала в окне −0,5…+5 с (при нескольких кандидатах — ближайший).
12. `stale` вычисляется только для успешных запусков; в причины не входят изменение `targetPorts` и версия движка (она лишь
    записывается в запуск); корпус через API неизменяем, так что причина «состав корпуса изменился» возможна только при ручной
    правке `project.json`.
13. Нарушения полей внутри `partial`/`ambiguous` сообщений попадают в находки, но не в счётчик `violations` (он считает
    сообщения со статусом `violation`); неописанные байты `partial`-сообщений не входят в `unknownBytes`. Нарушение поля
    внутри массива намеренно даёт три находки — для массива, элемента и поля (6.4).

**Хранение, задачи, интерфейсы**

14. Каждое изменение перезаписывает весь `project.json`; блокировки между процессами нет (два экземпляра на одном каталоге
    опасны); после `rename` каталог не синхронизируется (`fsync` каталога нет), а файл записи и распакованные файлы
    архива не синхронизируются до того, как на них сошлётся `project.json`; если сохранение не удалось, изменение уже
    внесено в память, и до следующего успешного сохранения состояния памяти и диска расходятся. Правка гипотезы
    (`PATCH /hypotheses/{id}`) из двух вкладок — «побеждает последний»: версии объекта и проверки конфликтов нет.
15. Фоновые задачи не имеют очереди и ограничения параллелизма и не переживают перезапуск: после жёсткого завершения
    импорт записи возобновляется, а проверка или отчёт только помечаются `failed` («Прервано…») — их нужно запустить заново.
16. Нет аутентификации. Явный не-loopback `--addr` по замыслу отключает проверку `Host` (сервер открыт сети). В
    loopback-режиме допускается `Origin` любого loopback-адреса (нужно прокси dev-сервера Vite), поэтому страница другого
    локального порта в старом браузере без `Sec-Fetch-Site` может выполнить запросы без тела и multipart-загрузки (11.5).
    Центральный каталог zip читается `archive/zip` целиком до проверки «не больше 10 000 файлов» (его размер ограничен
    размером архива).
17. `http.Server` без `ReadTimeout`/`WriteTimeout` (потоковые загрузки и выгрузки). В режиме TUI ошибка `srv.Serve` не
    отслеживается до выхода из интерфейса.
18. `protolab verify` сравнивает сводки, а не находки. `apply` не применяет утверждения (журнала действий у него нет), всегда
    использует политику контрольных сумм `warn`.
    `targetPorts` не записываются в запуск проверки: в файл примеров попадают текущие порты проекта, и если их меняли после
    проверки (это не делает её устаревшей, п. 12), роли сессий без рукопожатия выводятся по другим портам, и сводка
    `verify` может не совпасть с ожидаемой.
19. Отчёт — Markdown и JSON (HTML нет); у отчёта нет поля с причиной сбоя (`failed` без текста). Свободный текст
    вставляется в Markdown без экранирования: `|` или перевод строки в назначении поля ломает таблицу полей, перевод
    строки в заметке или формулировке — строку списка.
20. `Limits.MaxMessageBytes` — справочное значение для `/system/info`; на деле верхний предел длины сообщения по умолчанию задаёт
    константа `engine.DefaultMaxLength` (65 600 Б) либо `maxLength` спецификации.
21. Нет отдельного нагрузочного теста с конкурентными HTTP-запросами; запуск процесса целиком (`runServe`: флаги, сигналы, TUI в
    настоящем терминале) автотестами не покрыт — его проверяет смоук-тест CI и ручной запуск.
22. Веб-интерфейс: удалить наблюдение можно только через API (`DELETE /observations/{id}`) — кнопки в интерфейсе нет; выбор
    интерпретации в рабочей области сессии предлагает только последнюю версию каждой интерпретации (сессия со старой
    версией открывается только по ссылке с параметром `v` — из примера находки, сравнения или редактора версии).
23. В репозитории пока нет файла лицензии проекта (`LICENSE`): релизные архивы содержат только `THIRD_PARTY_NOTICES.md`
    (`make release-local` скопирует `LICENSE*`, когда он появится).
